ADR (설계 결정 기록)

왜 이렇게 만들었는지를 나중에 다시 찾아보기 쉽도록, 코드에 남지 않는 의사결정 배경을 기록합니다. 새 결정이 생기면 이 아래에 계속 추가하세요.

ADR-001 — 모노레포 의존성 관리 도구: pnpm workspaces

상태Accepted · 상세 원문은 docs/monorepo-dependency-management.md

배경 (Context)

meta-scan-api(Express + TypeScript, 원래 npm)와 meta-scan-front (Next.js, 원래 pnpm)를 git subtree로 packages/* 아래 합쳐 하나의 모노레포(meta-scan)로 구성하는 과정에서, 두 패키지가 서로 다른 패키지 매니저를 쓰고 있었기 때문에 워크스페이스 전체를 관리할 단일 도구가 필요했습니다. 후보는 pnpm workspaces와 Yarn Berry(Yarn 2+, PnP) 두 가지였습니다.

결정 (Decision)

  • 루트에 pnpm-workspace.yaml(packages/*)과 루트 package.json(packageManager: pnpm@10.15.0 고정 + 공통 스크립트) 추가
  • 패키지별 lockfile(meta-scan-api의 package-lock.json, meta-scan-front의 pnpm-lock.yaml)을 삭제하고 루트 pnpm-lock.yaml 하나로 통합
  • meta-scan-front의 package.json name이 루트와 같은 "meta-scan"이라 --filter 대상이 모호해지는 문제를 "meta-scan-front"로 변경해 해결
  • puppeteer/esbuild/sharp 등 네이티브 설치 스크립트가 있는 의존성은 루트 pnpm.onlyBuiltDependencies에 명시적으로 허용 등록(pnpm은 기본적으로 install script를 차단하기 때문)

고려한 대안 (Alternatives Considered)

비교 항목pnpm workspacesYarn Berry (PnP)
기존 상태와의 정합성front가 이미 pnpm 사용 중 → 마이그레이션 비용 최소front(pnpm→yarn), api(npm→yarn) 둘 다 전환 필요
네이티브 의존성 호환성puppeteer/lighthouse 같은 네이티브 바이너리와 문제 이력 적음PnP 모드에서 네이티브 addon과 호환성 이슈 이력 다수 — 실무에서 node-modules 모드로 우회하는 경우가 많음
Next.js 호환성공식 지원, 이슈 적음PnP 모드에서 과거 이슈 다수 리포트됨
학습/마이그레이션 비용낮음 — npm/yarn과 사용법 거의 동일상대적으로 높음 — .yarnrc.yml, zero-install, PnP 개념 학습 필요

전체 비교표와 마이그레이션 6단계는 docs/monorepo-dependency-management.md에 원문 그대로 있습니다.

결과 (Consequences)

얻은 것
  • front 쪽 마이그레이션 비용 거의 없음(이미 pnpm 사용 중이었음)
  • puppeteer/lighthouse 등 네이티브 의존성 관련 호환성 리스크 회피
  • Next.js 공식 지원 + 생태계 사례(Vite/Turborepo/Vue 등)가 pnpm 쪽에 풍부
트레이드오프
  • pnpm의 엄격한 phantom dependency 방지 때문에, 새 네이티브 의존성을 추가할 때마다 onlyBuiltDependencies에 수동으로 등록해야 함(안 하면 postinstall이 조용히 스킵됨)
  • 빌드 캐싱/파이프라인(Turborepo, Nx 등)은 아직 도입하지 않음 — 향후 고려 사항으로만 남아있음

ADR-002 — pre-commit/commit-msg 훅으로 린트·커밋 포맷 강제

상태Accepted · 2026-08-13

배경 (Context)

저장소를 스캔한 결과 테스트/CI/CD/브랜치 전략/커밋 컨벤션이 전무했고 (설계 페이지 2장 참고), 두 패키지의 ESLint 규칙 (@typescript-eslint/no-unused-vars, no-explicit-any 등)이 완전히 따로 관리돼 시간이 지날수록 규칙이 서로 어긋날 위험이 있었습니다.

결정 (Decision)

  • 루트에 husky(v9) + lint-staged + commitlint (@commitlint/config-conventional)를 devDependency로 추가
  • pre-commit: lint-staged가 스테이지된 파일만 골라 패키지별로 pnpm --filter <pkg> exec eslint --fix 실행
  • commit-msg: commitlint가 Conventional Commits 형식을 강제
  • 두 패키지가 겹치는 TypeScript 규칙만 eslint.config.base.mjs로 분리해 공유 (Next.js 전용 규칙 등 프레임워크 특화 부분은 각자 유지 — 설계 1.2/1.3 참고)

고려한 대안 (Alternatives Considered)

대안기각 사유
아무것도 안 함 (수동 규율에 의존)이미 컨벤션 부재가 확인된 상태 — 재발 가능성이 높다고 판단
simple-git-hooks 같은 더 가벼운 훅 러너더 가볍지만 lint-staged와의 조합 사례가 husky만큼 널리 쓰이지 않아, 앞으로 유지보수할 사람이 정보를 찾기 쉬운 쪽(husky)을 택함
로컬 훅 대신 GitHub Actions CI로 강제이 저장소엔 CI/CD 자체가 없고, 이번 스코프를 로컬 훅으로 한정함 — 서버 강제는 별도 ADR 대상
두 패키지 ESLint를 완전히 하나의 config로 통합meta-scan-front는 next/core-web-vitals 등 Next.js 전용 규칙이 필요해 100% 동일한 config는 기술적으로 맞지 않음 — 겹치는 규칙만 공유하는 절충안 채택

결과 (Consequences)

얻은 것
  • 커밋 로그가 파싱 가능한 형태로 통일 (향후 changelog 자동화 여지)
  • 스테이지된 파일만 검사해 커밋 시 오버헤드가 적음
  • 두 패키지의 미사용 변수/any 처리 규칙이 더 이상 따로 놀지 않음
트레이드오프
  • 새 devDependency 4종 추가(husky, lint-staged, commitlint 2종)
  • 로컬에서만 강제됨 — pnpm install을 안 하거나 --no-verify로 우회하면 그대로 통과됨(CI/CD 부재와 연결되는 한계)
  • 이 시점 이전 커밋 히스토리는 형식이 소급 적용되지 않음

ADR-003 — 유저 플로우 통합: 4-API 오케스트레이션 + 프론트 스코어링 유지

상태Accepted · 2026-08-13 (기획 인터뷰로 확정, 구현 착수 전 — PRD 페이지 3장에 결과 반영)

배경 (Context)

PRD가 제안한 TO-BE(단일 POST /api/v1/scan/analyze 엔드포인트로 4개 API 호출을 대체)와 실제 코드의 AS-IS(ProcessScreen이 4개 API를 병렬 호출하지만 응답을 버리고 /scan은 Math.random() 목업을 렌더) 사이에 다음 충돌/공백이 확인됐습니다:

  • /api/v1/scan/analyze 엔드포인트와 스코어링 엔진이 실제로는 존재하지 않음
  • AI 신호 추출 로직(구조화 데이터/prompts.txt/FAQ 등)이 백엔드 어디에도 없음
  • TO-BE가 전제하는 zustand 상태전달과 달리 scanStore.ts는 미사용 죽은 코드이고 /scan은 서버 컴포넌트
  • API 호출이 4개→1개로 줄면 ProcessScreen의 5단계 진행 UI가 실제 진행률을 반영할 수 없게 됨
  • 기존 4개 개별 API 함수가 단일 엔드포인트로 대체되면 사실상 미사용 코드가 될 상황

결정 (Decision)

  • 상태 전달은 PRD대로 zustand 스토어 — /scan을 클라이언트 컴포넌트로 전환하고 scanStore.ts를 재구현해 분석 결과(url → 원본 응답 + 점수)를 저장·조회
  • 단일 scanAnalyzeApi로 교체하지 않고, 기존 4개 API(robots/sitemap/ crawling/lighthouse) 호출을 그대로 유지 — ProcessScreen의 5단계 진행 애니메이션이 각 API의 실제 완료 시점에 반응하도록 하고 싶다는 요구가 우선했음
  • 각 API 완료마다 결과를 버리지 않고 저장, 4개가 다 모이면 프론트 유틸 (computeAiPreparedness)이 클라이언트 사이드에서 점수를 계산
  • 단, AI 신호의 원본 필드(구조화 데이터, prompts.txt, hreflang 등)는 DOM 접근이 필요해 crawling API 응답 확장(백엔드)이 선행 조건으로 남음 — "프론트 계산"은 가중합산 로직만 프론트로 가져온다는 뜻이지 백엔드 작업이 없어진다는 뜻이 아님

고려한 대안 (Alternatives Considered)

대안기각 사유
PRD 원안: 신규 /analyze 단일 엔드포인트 + 서버 스코어링실시간 단계별 피드백(각 API 완료마다 UI 반영)을 유지하고 싶다는 요구와 맞지 않음 — 단일 호출은 완료 시점이 하나뿐이라 5단계 UI를 실제 진행률로 채울 수 없음
5단계 UI를 단일 로딩 인디케이터로 단순화애니메이션 자체는 유지하고 싶다는 요구가 있었음 — 대신 "가짜"가 아니라 실제 API 완료 이벤트에 반응하도록 개선하는 쪽을 택함
AI 신호/점수 계산을 위한 새 5번째 API(scanAiSignalsApi) 신설5단계 UI와 1:1로 깔끔하게 맞지만, crawling과 별도로 페이지를 한 번 더 로드해야 해서 Puppeteer 크롤링이 중복됨(PRD가 애초에 페이지를 두 번 안 읽으려고 getOnloadHtml 확장을 권장한 이유와 배치)
점수 계산을 crawling API 응답 확장과 함께 백엔드에서 처리기술적으로는 더 깔끔하지만, 지금 단계에서는 백엔드 변경 없이 빠르게 시작할 수 있는 프론트 계산 쪽을 우선하기로 함

결과 (Consequences)

얻은 것
  • PRD 원안보다 변경 범위가 작음 — 라우팅/오케스트레이션 구조를 갈아엎지 않고 "결과를 버리지 않게 고치기 + 점수 계산 얹기"로 축소됨
  • 진행 UI가 실제 이벤트 기반이 되어 사용자 신뢰도가 올라감(가짜 progress 제거)
  • 기존 4개 API가 계속 실사용되므로 "죽은 코드가 될 위험" 자체가 해소됨
트레이드오프
  • crawling 백엔드 확장은 여전히 필요 — "프론트 계산"이 백엔드 작업을 없애주지 않음
  • prompts.txt 배치 방식, 캐시 도입 여부는 이번에 결정하지 않고 구현 시점으로 미룸(PRD 페이지 3.2 참고)
  • PRD 문서(5.2/6/7장)의 /analyze 엔드포인트 관련 서술은 이 ADR로 대체됨 — PRD 원문 자체는 아직 갱신하지 않았으므로 PRD md를 읽을 땐 이 ADR이 최신 결정임을 감안할 것

ADR-004 — 디자인 시스템: 토큰 기반 + data-theme 다크모드로 전환

상태Accepted · 2026-08-13 — 디자인 시스템 페이지에 결과 반영

배경 (Context)

meta-scan-front 전 화면이 shadcn 기본 스캐폴드 토큰 위에, 실제로는 요소마다 theme === "dark" ? "..." : "..." 삼항 연산자로 cyan→purple→pink 그라디언트· backdrop-blur·glow 섀도우를 직접 나열하고 있었습니다("AI 생성 티"). 추가로 다음이 확인됐습니다:

  • components/ui/*(button/badge/tabs)는 이미 Tailwind dark: 클래스로 작성돼 있었는데, 이를 앱의 테마 쿠키(data-theme)와 연결하는 @custom-variant dark 선언이 주석 처리된 채 방치돼 OS prefers-color-scheme을 따르는 실제 버그였음
  • 점수/상태 색(cyan/purple/pink)이 등급과 무관하게 장식적으로만 쓰이고 있었음
  • 푸터의 SCANS: 247,891 조작된 통계, 에러 화면의 잘못된 문구 재사용 등 콘텐츠 버그가 동반돼 있었음

결정 (Decision)

  • 화이트/차콜 중립 + 인디고 단일 포인트 컬러로 토큰 재정의(globals.css), 라이트는 :root, 다크는 :root[data-theme="dark"]에 동일 변수명으로 선언
  • 주석 처리돼 있던 @custom-variant dark ([data-theme=dark])를 활성화 — components/ui/*와 나머지 화면의 다크모드 소스를 data-theme 쿠키 하나로 통일
  • 점수/상태 색을 success/warning/destructive 시맨틱 토큰으로 고정 매핑(score >= 80 ? success : score >= 60 ? warning : destructive)
  • 그림자를 순수 검정 대신 인디고 색조로 틴트
  • components/ui/*의 cva/cn/data-slot 골격, templates/*의 theme/lang/t props drilling 구조는 그대로 유지 — 바뀐 건 참조하는 토큰 값과 스타일링 클래스뿐

고려한 대안 (Alternatives Considered)

대안기각 사유
다른 비주얼 톤(터미널/인더스트리얼-브루탈리스트 등)사용자가 3가지 스타일 프리뷰(미니멀·에디토리얼 / 터미널·진단툴 / 프리미엄 SaaS) 중 프리미엄 SaaS를 직접 선택 — 화이트 베이스 + 단일 포인트 컬러 방향으로 확정
아이콘 세트 교체(Lucide → Phosphor 등)redesign-existing-projects 스킬 감사 기준으로는 "Lucide 전량 사용"도 지적 대상이지만, 이번 요청의 핵심은 색상/그라디언트 제거였고 아이콘 교체는 스코프 확장 대비 이득이 낮다고 판단해 이번 라운드에서 보류
컴포넌트 라이브러리 자체 교체기각 — 기존 cva/radix 골격이 이미 토큰 기반으로 짜여 있어 팔레트만 바꾸는 쪽이 훨씬 저렴하고 안전함
실데이터 연동(/api/v1/scan/analyze)까지 같이 진행사용자가 명시적으로 스코프 제외 — "실데이터는 기획이 완료되면" 별도로 진행하기로 확정(ADR-003과 별개 트랙)

결과 (Consequences)

얻은 것
  • "AI 생성 티" 제거 — 그라디언트/blur/glow/조작된 통계 전량 삭제
  • 다크모드가 실제로 쿠키 하나로 통제됨(기존 버그 수정)
  • 점수/상태 색이 의미를 갖게 됨(등급 ↔ 색 고정 매핑)
  • 부수적으로 발견한 버그도 같이 수정: 에러 화면 문구 오사용, 디버그 console.log, complite 오타
트레이드오프
  • 아이콘/모션/카피 클리셰 등 다른 "AI 작업티" 축은 이번에 다루지 않음
  • /scan은 여전히 Math.random() 목업 — 새 토큰으로 껍데기만 재작업됨
  • 완전 커스텀 루트 404는 미해결 — 진짜 루트 app/layout.tsx가 없는 기존 구조 때문에 루트 app/not-found.tsx를 붙이면 빌드 에러가 나서(실제로 시도 후 롤백) 레이아웃 구조 변경이 선행돼야 함
