ADR (설계 결정 기록)

왜 이렇게 만들었는지를 나중에 다시 찾아보기 쉽도록, 코드에 남지 않는 의사결정 배경을 기록합니다. 최신순(내림차순)으로 정렬돼 있습니다 — 새 결정이 생기면 규칙 카드 바로 다음(맨 위)에 추가하세요. 작성 규칙은 바로 아래 카드 참고.

ADR 작성 규칙 META

이 카드 자체도 아래 규칙을 따릅니다 — 규칙이 바뀌면 이 본문을 고치지 않고 맨 아래 변경 이력에 추가합니다.

1. 본문은 append-only — Accepted 이후 다시 쓰지 않는다

ADR 카드가 Accepted가 된 뒤에는 배경(Context)/결정(Decision)/ 고려한 대안(Alternatives)/결과(Consequences) 본문을 절대 고쳐 쓰지 않습니다. 그 시점에 실제로 어떤 근거로 무엇을 결정했는지를 있는 그대로 남기는 것이 ADR의 존재 이유이기 때문입니다. 이후 생각이 바뀌거나 방향이 전환되면:

  • 새 번호의 ADR을 추가하고, 관련된 예전 ADR과 서로 링크(#adr-00N)
  • 예전 ADR의 결정이 실질적으로 뒤집혔다면 상태 배지만 Superseded by ADR-00N으로 바꾸고, 본문은 그대로 둠 (예: 이번에 ADR-005가 스코어링을 폐기했지만 ADR-003의 "4-API 유지" 결정 자체는 안 뒤집혀서 ADR-003은 Accepted 그대로 — 상태 변경은 결정이 실제로 무효가 됐을 때만)

2. 날짜는 두 종류 — 작성일(고정) vs 변경 이력(누적)

  • 작성일: 상태 줄의 Accepted · YYYY-MM-DD가 최초 작성일입니다. 이 날짜는 본문과 마찬가지로 이후 절대 바꾸지 않습니다.
  • 변경 이력: 상태 배지 변경, 다른 ADR에서의 참조 추가처럼 카드에 손을 대야 하는 경우, 본문 대신 카드 맨 아래에 변경 이력 목록을 추가하고 YYYY-MM-DD — 무엇이 왜 바뀌었는지 (관련 ADR 링크) 형식으로 한 줄씩 append합니다. 이렇게 하면 git blame 없이도 카드 자체에서 ADR의 버전 이력이 보입니다.

변경 이력 없이 상태 배지만 슬쩍 바뀌어 있으면 안 됩니다 — 배지가 바뀔 땐 반드시 변경 이력 한 줄이 같이 붙어야 합니다.

ADR-012 — 테스트 러너: 프론트 Jest / 백엔드 Vitest (패키지별 다르게)

상태Accepted · 2026-08-24 — 원문은 docs/case-study/test-runner-survey.md, 이 결정을 쓰는 대상은 docs/harness/tdd-issue-loop.md(GitHub Issues 기반 interview→dev→test TDD 루프, 아직 미구현)

배경 (Context)

docs/harness/tdd-issue-loop.md(interview → dev → test 3-agent 루프)를 실제로 만들려면 dev/test agent가 돌릴 테스트 러너가 필요한데, meta-scan-front/ meta-scan-api 둘 다 테스트 스크립트가 없는 상태였습니다(package.json에 test 필드 자체가 없음). docs/case-study/dev-lifecycle-harness.md가 이미 "시작 순서 1순위"로 Vitest(front/api 공용)를 제안해뒀지만, 그 문서는 이번 결정과는 의도적으로 별개로 유지하기로 확인했습니다(두 문서가 서로 다른 에이전트 구조를 전제하기 때문 — tdd-issue-loop.md 상단 참고). 이번 결정은 그 로드맵을 그대로 가져오지 않고 docs/case-study/test-runner-survey.md로 Vitest/Jest/ node:test/Bun test를 이 저장소의 실제 제약(meta-scan-api가 "type": "module" 순수 ESM, tsx 기반 개발, Next.js 15 + React 19, 두 패키지가 다른 테스트 환경을 필요로 함) 기준으로 다시 비교해 도출했습니다.

결정 (Decision)

  • 기술적 추천은 "두 패키지 다 Vitest"였습니다 — ESM 트랜스파일 마찰이 가장 적고, vitest.workspace.ts 하나로 front(jsdom)/api (node) 환경을 함께 커버할 수 있어 리소스·유지보수 관점에서 가장 효율적이라고 판단했습니다.
  • 하지만 사용자가 이 프로젝트를 학습을 겸해 진행 중이라는 이유로 그 추천을 의도적으로 뒤집었습니다 — 원문 그대로: "나는 학습도 겸하기 위해 이 프로젝트를 진행중이니 프론트는 jest를 백엔(드는) vitest를 도입하자". 효율보다 "프론트/백엔드에서 서로 다른 러너를 실제로 각각 다뤄보는 경험"을 우선한 것으로, 기술적 판단이 틀려서가 아니라 목적 함수 자체가 다름을 명시적으로 밝힌 결정입니다.
  • 최종: meta-scan-front = Jest(next/jest 프리셋, jsdom 환경) / meta-scan-api = Vitest (node 환경).

고려한 대안 (Alternatives Considered)

대안기각/보류 사유
Vitest (front/api 둘 다) — 기술적 1순위 추천안기술적으로는 가장 효율적(ESM 마찰 최소, 워크스페이스 하나로 두 환경 커버)이지만, 학습 목적상 "서로 다른 러너를 각각 경험"이라는 목표에는 안 맞음 — 순수 리소스 효율보다 학습 가치를 우선하기로 함
Jest (front/api 둘 다)meta-scan-api가 순수 ESM이라 Jest 런타임의 ESM 지원이 여전히 --experimental-vm-modules 플래그가 필요한 준실험 상태이고, ESM의 live binding 특성 때문에 jest.mock()이 CJS 때보다 까다로움 (바벨/웹팩이 필수라서가 아님 — 이 부분은 최초 조사에서 부정확하게 서술했다가 정정함, test-runner-survey.md 1.2절 참고)
node:test (api만 우선 도입)의존성 0개·가장 빠르지만 React 컴포넌트 테스트(jsdom/@testing-library 통합)에 1급 지원이 없어 프론트에는 부적합 — 결국 프론트는 별도 러너가 또 필요해짐
Bun test빠르지만 별도 런타임을 pnpm/tsx/Docker 기반 배포 파이프라인에 새로 들여야 하는 비용이 이득보다 크다고 판단

결과 (Consequences)

얻은 것
  • 프론트/백엔드 각각에서 실제 러너를 다뤄보는 학습 경험 확보(이 프로젝트의 명시된 목적 중 하나)
  • meta-scan-api는 여전히 ESM 마찰이 가장 적은 Vitest를 채택 — 백엔드 쪽에서 기술적 이점은 그대로 유지됨
  • meta-scan-front는 Next.js 공식 프리셋(next/jest)의 이미지/폰트/CSS 모듈 목킹을 그대로 활용 가능
트레이드오프
  • 프론트(Jest)와 백엔드(Vitest)가 서로 다른 설정 체계·목킹 API(jest.mock vs vi.mock)를 쓰게 됨 — 저장소가 지금까지 지켜온 "두 패키지가 공유 설정 위에서 같은 도구를 쓴다"는 관행(예: eslint.config.base.mjs)과는 의도적으로 어긋남
  • CI 스크립트·문서·docs/harness/tdd-issue-loop.md의 dev/test agent 프롬프트를 패키지별로 각각 유지보수해야 함(agent가 이슈의 패키지 라벨을 보고 테스트 실행 커맨드를 분기해야 함)
  • docs/case-study/dev-lifecycle-harness.md가 제안해둔 "Vitest 둘 다" 시작 순서와는 다른 방향으로 확정됨 — 그 로드맵 문서는 의도적으로 손대지 않고 그대로 둠(두 문서가 서로 다른 전제 위에 있다는 걸 tdd-issue-loop.md에 이미 명시)

ADR-011 — 백엔드 아키텍처: Hexagonal (Ports & Adapters) 채택

상태Accepted · 2026-08-21 — 원문은 docs/case-study/backend-hexagonal-architecture.md(전체 후보 조사는 docs/case-study/backend-architecture-survey.md), 같은 날 구현 완료(원문 6장 "변경 이력" 참고)

배경 (Context)

ADR-010(프론트 Atomic Design + api/services/hooks)와 같은 맥락으로 meta-scan-api도 아키텍처를 재검토했습니다. 현재 구조(레이어드 router→controller→service)의 아픈 지점: scanService.ts가 ping/robotsTxt/ siteMap/crawling/checks를 전부 떠안은 "God 서비스"인 것, scanService가 Puppeteer/ChromeLauncher 구체 클래스에 직접 의존해 infra 교체·단위테스트 목킹이 어려운 것, 파일명 케이싱 불일치, lighthouse 모듈만 응답 규약을 깨는 것, 에러 원본을 삼키는 catch, 라우터마다 반복되는 수동 DI(패키지 CLAUDE.md에 이미 기록된 항목들).

ADR-009가 사용자 승인 없이 일방적으로 작성됐던 것이 확인된 뒤([ADR-010](#adr-010) 변경 이력 참고), "지금 도메인이 얕아 보인다는 이유로 계층을 미리 압축하지 않는다"는 원칙을 명시적으로 세우고 진행했습니다. 경로 별칭 스타일부터 (@core/*/@constant/*/@config/*/@infra/*/ @modules/* 5개 → meta-scan-front와 동일한 @/* 하나로 통일, 이 ADR과 무관한 선행 정리) 정리한 뒤, 7개 아키텍처 패턴(NestJS 기본 구조, Clean/ Onion, Hexagonal, DDD 모듈러 모놀리스, CQRS, Vertical Slice, 마이크로서비스)을 압축 없이 전부 조사(docs/case-study/backend-architecture-survey.md)했습니다.

결정 (Decision)

  • 계층/의존성 역전 축으로 확정 — CQRS(쓰기 경로 없음)와 DDD 모듈러 모놀리스(바운디드 컨텍스트가 사실상 1개)는 이 시점에 배제.
  • 같은 축 안에서 Clean/Onion(4계층: entities/use cases/interface adapters/frameworks)과 Hexagonal(3계층: 도메인+포트/애플리케이션/어댑터)을 실제 코드 예시로 구체 비교한 뒤, "entities 계층이 얕아 보인다"는 이유로 미리 기각하지 않고 PRD (docs/prd/meta-scan-plus-prd.md 3~4장)의 체크리스트 명세를 실제로 읽어 사실관계 확인 — 모든 체크 항목이 {id, group, label, status, detail?} 형태의 독립적· 무상태 분류 결과이며, 항목 간 관계 규칙·상태 변화·불변식이 명세 어디에도 없음을 확인(4장: 프론트 combineScanResults도 "계산이 아니라 취합"이라고 명시).
  • 이 사실을 근거로 Hexagonal (Ports & Adapters), 3계층 채택 — domain/(포트 인터페이스 + 순수 판정 로직) / application/ (유스케이스, 포트 호출 + 도메인 로직 조합) / adapters/(inbound: HTTP 컨트롤러, outbound: PuppeteerAdapter/ChromeLauncherAdapter가 기존 infra/Puppeteer.ts/infra/ChromeLauncher.ts를 감쌈). entities 별도 계층은 만들지 않음 — 위 사실 확인 근거.
  • 구현은 이번 ADR 범위 밖 — 방향만 확정, 세부(포트 세분화 수준, inbound 어댑터가 기존 modules/* 폴더링을 어떻게 흡수할지)는 실제 마이그레이션 시점에 확정. 상세는 docs/case-study/backend-hexagonal-architecture.md 5장.

얻은 것
  • Puppeteer/ChromeLauncher 교체·단위테스트 목킹이 포트 인터페이스 뒤로 숨겨져 쉬워짐 — docs/case-study/dev-lifecycle-harness.md 1순위인 테스트 인프라 작업과 직결
  • scanService God 서비스가 유스케이스별로 자연히 쪼개짐
  • 프론트 ADR-010의 "순수 로직(services/) vs I/O(api/)" 분리 철학과 백엔드가 같은 축(도메인 vs 어댑터)으로 맞춰짐
  • "도메인이 얕아 보인다"는 지레짐작이 아니라 PRD 명세를 실제로 읽고 확인한 사실 근거로 entities 계층 여부를 결정 — ADR-009 재발 방지 원칙 준수
트레이드오프
  • 포트를 얼마나 세분화할지 정답이 없어 설계자 재량에 좌우됨 — 실제 코드 작성 시점에 검증 전
  • entities 계층이 없어서, 나중에 체크 항목 간 관계/상태 규칙이 실제로 추가되면 재검토가 필요함(docs/case-study/backend-hexagonal-architecture.md 5장)
  • 에러 처리·파일명 케이싱·응답 규약 정리는 이 아키텍처 결정과 별개 이슈로 남겨둠 — 마이그레이션 실행 시점에 스코프를 따로 정해야 함

변경 이력

  • 2026-08-21 — 실제 마이그레이션 실행 완료. typecheck/build/ lint 통과 + 로컬 pnpm dev:api로 healthz/ scan/ping/scan/robotsTxt/scan/crawling/ lighthouse/run 전부 실제 호출 확인(뒤 둘은 포트를 통해 실제 브라우저를 띄우는 경로). 부수적으로 scanController.ts/scanService.ts의 파일명 케이싱 불일치(트레이드오프 항목 참고)가 이동 중 자연히 해소됨. 상세는 docs/case-study/backend-hexagonal-architecture.md 5~6장.

ADR-010 — 프론트 컴포넌트 아키텍처: Atomic Design 5계층 + api/services/hooks로 재결정

배경 (Context)

ADR-009(FSD-lite)가 사용자 인터뷰 없이 AI 세션이 일방적으로 작성한 결정이었던 것으로 확인되어 무효화됐습니다. 다뤄야 할 문제 자체(와이어프레임을 실제 코드로 옮길 때 "UI 컴포넌트"와 "기능(데이터 페칭·판정 취합·상태)"을 어떻게 분리할지)는 동일하지만, 이번엔 사용자와 AskUserQuestion으로 한 번에 하나씩 확인하는 순차 인터뷰를 거쳐 다시 결정했습니다. 인터뷰 도중 FSD-lite 압축(features+widgets 통합)이 "이 컴포넌트가 어느 계층인지" 애매함을 반복적으로 유발한다는 게 실제로 확인돼 (RootHeader/HeroSection 배치를 두고 세 차례 옵션 비교), 계층을 압축하지 않는 방향으로 바뀌었습니다.

결정 (Decision)

  • 정석 Atomic Design 5계층(atoms/molecules/organisms/ templates/pages)을 압축 없이 그대로 채택 — pages는 Next.js App Router의 app/[lang]/**/page.tsx가 겸함(별도 폴더 안 만듦)
  • Atomic Design은 "기능이 어디 사는지"를 정의하지 않으므로, 별도로 api/(네트워크 I/O, 목킹 필요) / services/(순수 로직 — combineScanResults, ADR-006 게이팅, 목킹 불필요) / hooks/(클라이언트 컴포넌트 전용 React 상태·React Query 자리) 3계층을 얹음
  • 서버 컴포넌트는 훅을 못 쓴다는 사실 확인: request-scan/page.tsx· scan/page.tsx는 서버 컴포넌트라 애초에 React 훅 사용이 불가능함(반면 ProcessScreen.tsx는 "use client") — loaders/ 같은 대칭 폴더를 새로 만들지 않고, 서버 컴포넌트는 지금처럼 api/를 직접 호출하는 Next.js 관용 패턴을 유지하기로 함
  • React Query 도입 방향은 확정했지만 실제 설치 + QueryClientProvider 배선은 새 인프라 작업이라 이번 스코프 밖 — hooks/ 폴더 자리만 예약
  • 이번 마이그레이션 패스의 범위는 "순수 이동 + 빈 세그먼트 TODO 스텁"으로 한정: ProcessScreen.tsx처럼 UI와 API 호출이 이미 섞여 있는 기존 파일은 쪼개지 않고 통째로 이동하고, templates/(Atomic) 계층의 실제 조립 파일(예: HomeTemplate)은 이번엔 만들지 않고 빈 폴더로 남김 — 둘 다 후속 작업
  • 구체적 파일 이동 매핑은 docs/case-study/frontend-atomic-architecture.md 4장 참고

고려한 대안 (Alternatives Considered)

대안기각/보류 사유
FSD 계열 4계층 압축판 (ADR-009 원안)승인 절차 문제와 별개로, 압축 자체가 "이 컴포넌트가 어느 계층인지" 애매함을 반복 유발함이 이번 인터뷰 중 재확인됨
정석 FSD 6계층사용자가 "6계층이 모두 필요할 것 같다"는 문제의식으로 이 재논의를 시작했으나, 최종적으로는 Atomic Design 쪽을 선택 — FSD는 "기능이 어디 사는가"엔 강하지만 이번 팀 규모·도메인엔 Atomic의 UI 세분화 축이 더 필요하다고 판단

얕은 features/ 폴더를 Atomic과 혼용한 슬라이스만 다른 패러다임(FSD풍)을 쓰면 "이건 어디 있지" 혼란이 재발할 가능성 — Atomic 채택 결정과 직접 모순

결과 (Consequences)

얻은 것
  • 계층을 압축하지 않아 "이 컴포넌트가 어느 계층인지" 판단 규칙이 명확함(복잡도 기준)
  • api/services/hooks 분리로 테스트 전략이 계층별로 갈림 — services는 목킹 없이, hooks는 통합 테스트로
  • 서버/클라이언트 컴포넌트가 React 훅 가용 여부부터 다르다는 사실을 폴더 구조에 반영해, 나중에 "왜 이 페이지엔 훅이 없지"라는 혼란을 방지
  • 실제 사용자 순차 인터뷰를 거쳐 결정 — ADR-009가 겪은 승인 절차 문제 재발 방지
트레이드오프
  • 정석 5계층이라 폴더 수가 FSD-lite보다 많음 — 이번 앱 규모(단일 스캔 도메인)엔 과할 수 있다는 우려가 여전히 남음(3장 참고)
  • templates/(Atomic) 계층과 hooks/의 React Query 배선은 이번에 비워둬서, 실제로 잘 맞는 경계인지는 다음 패스에서 검증 전
  • services/combineScanResults.ts·scanGating.ts는 TODO 스텁만 있고 실제 판정 로직은 여전히 없음 — 폴더 구조만 준비된 상태

변경 이력

  • 2026-08-21 — 실제 이동 실행 중 사용자 제안으로 atoms/molecules/ organisms/templates 4개를 ui/ 하위로 재중첩 (ui/atoms/ 등) — "UI vs 기능" 분리를 src/ 최상위에서 바로 드러내기 위함. api//services//hooks/는 ui/와 형제 레벨로 최상위에 그대로 둠. 이 결정의 핵심(계층 자체, 기능 3분리)은 안 바뀌었고 물리적 중첩 위치만 조정 — 상세는 docs/case-study/frontend-atomic-architecture.md 6장.

ADR-009 — 프론트 컴포넌트 아키텍처: FSD-lite로 UI/기능 분리

상태Superseded by ADR-010 · 2026-08-18 — 원문은 docs/case-study/frontend-component-architecture.md

배경 (Context)

docs/design/design-system.md(ADR-008, 진 인덱스 톤)로 확정된 와이어프레임 캔버스를 실제 meta-scan-front 코드로 옮기기에 앞서, "UI 컴포넌트"와 "기능(데이터 페칭·판정 취합·상태)"을 어떻게 분리할지가 정해지지 않은 상태였습니다. 지금 남은 진짜 작업(ProcessScreen이 4개 API 응답을 버리는 것, /scan이 Math.random() 목업인 것, combineScanResults 취합 로직이 없는 것 — CLAUDE.md 참고)이 전부 "기능" 쪽에 몰려 있어서, 이 경계를 명확히 긋는 것이 목적이었습니다.

결정 (Decision)

  • 정석 FSD(Feature-Sliced Design) 6계층(app/pages/ widgets/features/entities/shared)이 아니라, features와 widgets를 통합한 4계층 "FSD-lite"를 채택 — shared / entities(도메인 얕아 당장은 생략 가능) / features / pages(=Next.js app/[lang]/**/page.tsx)
  • 핵심 규칙: shared/는 API 호출·스토어를 모르고 props만 받는다. API 호출·판정 취합(combineScanResults)· ADR-006 게이팅 로직은 반드시 해당 feature 슬라이스의 model/ 또는 api/ 세그먼트 안에만 존재하고, ui/ 세그먼트나 shared/로 새지 않는다
  • 기존 폴더와의 충돌 지점 정리: src/apis/는 공유 인스턴스만 shared/api로, 도메인별 호출은 각 feature 슬라이스로 이동 / src/stores/scanStore.ts는 당분간 shared/에 유지(도메인이 얕아 entities 승격은 보류) / src/templates/는 이름을 유지한 채 FSD의 features+widgets 역할을 흡수 / src/app/[lang]/는 Next.js App Router가 이미 그 이름을 쓰고 있어 FSD app 레이어를 별도 폴더로 만들지 않고 layout.tsx + src/providers/로 흡수
  • 구현은 이번 ADR 범위 밖 — 방향만 확정, 슬라이스 경계 세부(예: toggle-checklist-item을 run-scan 안에 둘지 분리할지)는 실제 컴포넌트 작성 시점에 확정

고려한 대안 (Alternatives Considered)

대안기각/보류 사유
기존 2계층 그대로 확장 (components/ui/ + templates/)컨벤션일 뿐 강제력이 없음 — templates/가 커지면서 UI와 기능이 다시 섞일 위험
훅(hooks) 계층 분리 (useProcessScan() 등으로 데이터 페칭 캡슐화)목적 자체는 FSD의 model/api 세그먼트와 사실상 같음 — FSD 채택으로 흡수됨
design-system/ 폴더 신설 + ESLint import-boundary로 강제컴파일타임 강제라는 장점은 있으나, 디자인 시스템이 막 확정된 시점(ADR-008 당일)이라 폴더 구조까지 못 박기엔 이름
Atomic Design 정석 5단계(atoms/molecules/organisms/templates/pages)단일 스캔 플로우라 atom/molecule 경계 논쟁이 잦고, templates/라는 이름이 기존 의미와 충돌

FSD 정석 6계층도메인이 얕아(entities 1~2개) 계층 일부가 형식적 껍데기만 남음
Atomic(형태)+FSD(경계) 하이브리드자체 조합이라 온보딩 설명 비용이 가장 큼

결과 (Consequences)

얻은 것
  • "UI 컴포넌트는 기능을 모른다"는 경계가 폴더 세그먼트(ui vs model/api) 단위로 명시적으로 정의됨
  • 남은 작업(4-API 취합, ADR-006 게이팅)이 정확히 features/run-scan 슬라이스 하나로 매핑돼 구현 범위가 뚜렷함
  • 정석 6계층 대비 이 앱 규모(단일 도메인)에 맞게 계층 수를 줄여 형식적 폴더가 생기지 않음
트레이드오프
  • "정석" FSD가 아니라서 FSD를 아는 사람이 합류하면 widgets/ entities가 왜 없거나 통합됐는지 설명이 필요함
  • 구현 전이라 슬라이스 경계가 실제로 잘 맞는지는 검증되지 않음 — 컴포넌트를 만들면서 조정될 수 있음
  • src/components/ui/(기존 shadcn 프리미티브)와 새 shared/의 관계(완전 대체 vs 공존)는 이번에 정하지 않음

변경 이력

  • 2026-08-21 — 이 결정이 실제로는 사용자와 함께 진행되지 않고 AI 세션이 일방적으로 작성한 것으로 확인됨(사용자 확인: "이러한 결정을 같이 진행한 바가 없어"). 사용자와 단계별 확인(AskUserQuestion)을 거쳐 다시 결정한 ADR-010(Atomic Design 5계층)으로 대체 — 이 카드의 본문(배경/ 결정/대안/결과)은 원 기록으로 그대로 두고 상태 배지만 변경.

ADR-007 — Lighthouse 개별 감사(lhr.audits) 재사용: 결과 화면 하단 "Lighthouse 개선 제안" 카드

상태Accepted · 2026-08-18

배경 (Context)

PRD 3.7절은 "Lighthouse는 4개 숫자 점수만 유지하고 개별 감사(lhr.audits)는 재사용하지 않는다"고 정했었습니다(ADR-003의 "crawling 독립성 유지" 취지를 Lighthouse에도 적용한 것). 그런데 결과 화면 하단에 Hero("지금 고쳐야 할 것")와 별개로 "개선 제안" 카드를 배치하는 과정에서, 이 카드를 자체 체크리스트(checks[]) 재노출이 아니라 Lighthouse가 이미 계산해주는 감사 항목(opportunities/diagnostics) 으로 채우는 쪽이 사용자 의도임이 확인됐습니다. 코드 확인 결과 LighthouseController가 이미 result?.lhr 전체(audits 포함)를 그대로 반환하고 있어, 백엔드 파싱 추가 없이 프론트에서 바로 소비 가능하다는 것도 함께 확인됐습니다.

결정 (Decision)

  • 결과 화면 하단 "Lighthouse 개선 제안" 카드는 자체 checks[]가 아니라 lighthouse run 응답의 lhr.audits에서 점수가 낮은 opportunity/ diagnostic 항목을 추려 보여줌
  • Hero("지금 고쳐야 할 것")는 계속 자체 checks[] 기반 topIssues 그대로 — 두 영역은 출처가 다름을 화면에서 명확히 구분(Hero = 우리 판정, 하단 = Lighthouse 자체 판정)
  • 신규 백엔드 엔드포인트·필드 불필요 — lhr.audits가 이미 응답에 포함돼 있어 프론트가 그중 일부만 골라 렌더링
  • PRD 3.7절의 "개별 감사(lhr.audits)도 재사용하지 않습니다" 문구는 이 결정으로 뒤집힘 — PRD 원문(docs/prd/meta-scan-plus-prd.md, PRD 페이지)에 직접 반영(PRD는 ADR과 달리 append-only 대상이 아님)
  • ADR-003의 핵심 결정(4개 API 오케스트레이션, 신규 /analyze 엔드포인트 없음)은 그대로 유지 — crawling/lighthouse는 여전히 별도 API 호출이며, 이번 결정은 "이미 받은 응답 중 무엇을 재사용하는가"만 넓힌 것

고려한 대안 (Alternatives Considered)

대안기각 사유
하단 카드도 자체 checks[] 재노출(직전 초안)Hero에서 이미 본 내용과 중복 — Lighthouse가 이미 계산해주는 정보를 활용하는 쪽이 정보 가치가 더 큼
lhr.audits 전체를 그대로 나열보통 수십 개 항목이 있어 그대로 노출하면 과함 — opportunity/diagnostic 중 점수 낮은 것만 추리는 쪽으로 확정

결과 (Consequences)

얻은 것
  • Lighthouse가 이미 계산한 데이터를 재사용 — 신규 판정 로직·백엔드 변경 불필요
  • Hero(자체 판정)와 하단(Lighthouse 판정)의 출처가 분리돼 사용자에게 더 명확함
트레이드오프
  • 프론트가 lhr.audits 스키마(score, details.type 등)를 이해하고 필터링 로직을 가져야 함 — 어떤 기준으로 몇 개를 뽑을지는 구현 시점에 확정 필요
  • ADR-003이 원래 내세운 "crawling 독립성 유지" 취지와는 부분적으로 어긋남(Lighthouse 응답을 화면 구성에 다시 끌어옴) — 다만 API 호출 구조 자체는 안 바뀌므로 ADR-003 본문은 Accepted 그대로 두고 상태 변경은 하지 않음

ADR-006 — robots.txt 선검사 게이팅: 비허용 시 전체 스캔 하드 차단

상태Accepted · 2026-08-18

배경 (Context)

기존 ProcessScreen은 robots/sitemap/crawling/lighthouse 4개 API를 Promise.allSettled로 **동시에** 호출합니다. robots.txt가 스캔을 명시적으로 차단(disallow)하는 사이트여도 나머지 3개(특히 Puppeteer 크롤링과 Lighthouse — 둘 다 헤드리스 Chrome을 띄우는 비용이 큰 작업)가 이미 병렬로 실행되고 난 뒤에야 결과 화면에서 "허용 안 됨"이 드러나는 구조였습니다. 사용자가 비용 절감을 이유로 이 순서를 바꾸길 원했습니다.

결정 (Decision)

  • robots.txt를 1차로 단독 실행 — ProcessScreen이 4개를 한 번에 병렬 호출하지 않고, robots.txt 결과를 먼저 await
  • 비허용(disallow) 판정 시 완전 하드 차단 — sitemap/crawling/lighthouse 3개를 아예 호출하지 않고 즉시 중단, "이 사이트는 검사할 수 없습니다" 안내만 표시(경고 후 진행 옵션 없음)
  • 허용 시에만 나머지 3개(sitemap/crawling/lighthouse)를 Promise.allSettled로 병렬 실행 — 이 부분은 기존 구조와 동일
  • 차단 화면은 기존 ErrorScreen과 별도의 신규 컴포넌트로 분리 — "사이트 접속 실패"(네트워크/서버 문제)와 "접속은 되지만 robots.txt가 차단"은 원인이 달라 사용자에게 정확한 이유를 전달할 필요가 있음

고려한 대안 (Alternatives Considered)

대안기각 사유
경고만 표시하고 사용자가 원하면 계속 진행비용 절감이 목적인데 사용자가 계속 진행을 누르면 절감 효과가 사라짐 — 사용자가 직접 "완전 차단"을 선택
차단 화면을 ErrorScreen 재사용, 메시지만 분기구현은 더 단순하지만 "접속 실패"와 "차단"이 사용자 입장에서 다른 상황이라 원인 전달이 흐려짐 — 사용자가 직접 신규 화면을 선택

결과 (Consequences)

얻은 것
  • robots.txt가 차단한 사이트에서 Puppeteer/Lighthouse를 아예 실행하지 않아 비용 절감
  • 크롤링 윤리 측면에서도 사이트 소유자 의사를 존중하는 방향과 일치
  • /scan 결과 화면의 Indexing 카드에서 "robots.txt 허용" 항목이 사실상 중복 제거됨 — 여기 도달했다는 것 자체가 이미 허용됐다는 뜻이라 별도 배지로 보여줄 필요가 없어짐 (PRD 페이지 참고)
트레이드오프
  • 4개 API가 완전 병렬이 아니게 됨 — robots.txt 완료까지는 다른 3개가 대기, 정상 사이트 기준으로 체감 스캔 시간이 robots.txt 응답 시간만큼 늘어남
  • 신규 화면 컴포넌트(가칭 BlockedScreen.tsx) 하나가 추가로 필요
  • 어떤 user-agent 규칙을 기준으로 허용/비허용을 판단할지(와일드카드 * vs 특정 봇 이름)는 이번에 확정하지 않음 — 구현 시점에 * 규칙을 기본으로 결정 필요

ADR-005 — 스코어링 엔진 폐기, 체크리스트(pass/warning/fail/info)로 전환

상태Accepted · 2026-08-18 — docs/prd/meta-scan-plus-prd.md·PRD 페이지에 결과 반영

배경 (Context)

사용자와 대화하며 확인된 사실: PRD의 "0–100점 AI Preparedness Index" 가중합산 스코어링 개념은 사용자 본인이 낸 기획이 아니라 이전 세션에서 AI가 기획하며 덧붙인 것이었습니다. 사용자의 원래 의도는 "크롤링 결과를 SEO/AEO 체크리스트로 점검해주는" 수동적 진단 도구였고, 수익 모델도 Google 애드센스(무료·고트래픽·광고 기반)라 점수 합산·가중치·등급 같은 프리미엄 진단 제품의 문법과 맞지 않았습니다. 이 불일치가 "기획에 확신이 안 선다"는 감각의 실제 원인으로 확인됐습니다.

결정 (Decision)

  • 0–100 가중합산 스코어링 엔진(원 PRD 4절, topFixes 생성 로직 포함)을 전량 폐기
  • 각 체크 항목은 가중치 없이 pass / warning / fail / info 넷 중 하나로만 판정 — 합산 점수·등급 없음
  • 결과 화면 Hero(기존 "AI Preparedness Score" 큰 숫자)는 fail 항목 상위 N개를 강조하는 카드로 교체("점수가 낮습니다"가 아니라 "지금 고쳐야 할 것")
  • Lighthouse 4개 점수(performance/seo/accessibility/best-practices)는 예외 — 구글 자체 채점 기준이라 숫자 그대로 유지, 우리 체크리스트 판정 대상에서 제외
  • ADR-003의 아키텍처 결정(4개 API 유지, 신규 /analyze 엔드포인트 없음, 프론트에서 계산)은 그대로 유지 — 바뀐 건 "무엇을 계산하는가"(점수 → 체크리스트 판정)뿐, "어디서 계산하는가"는 그대로. 프론트 유틸 이름도 computeAiPreparedness → computeChecklist로 변경
  • 체크리스트 완성 후 FAQ 스키마(schema.org FAQPage) 생성 도구(진단이 아니라 처방 — 감지된 신호 부재를 보고 실제 콘텐츠 기반 FAQ 스키마를 생성)를 다음 단계로 계획, 이번 스코프에는 포함하지 않음

고려한 대안 (Alternatives Considered)

대안기각 사유
스코어링 엔진 유지, 가중치만 재조정근본 문제가 가중치 튜닝이 아니라 "점수 합산이라는 제품 형태 자체가 사용자 기획과 다르다"는 것이었음 — 튜닝으로 해결 안 됨

ADR-003도 함께 재검토(백엔드 단일 엔드포인트로 재전환)실수로 초안에서 잠깐 되돌아갔었으나, ADR-003의 근거(단계별 진행 UI가 실제 이벤트에 반응)는 스코어링 폐기와 무관하게 여전히 유효 — ADR-003은 그대로 유지하기로 확정

결과 (Consequences)

  • 가장 복잡하고 주관적이었던 부분(가중치 합산 규칙)이 통째로 사라져 구현 범위가 단순해짐 — 순수 룰 판정 함수만 남음
  • 기획이 사용자 본인 의도와 다시 일치 — "확신이 안 선다"던 근본 원인 해소
  • 애드센스(무료·고트래픽) 수익 모델과 제품 톤이 맞춰짐
트레이드오프
  • 화면 UI가 다시 손이 감 — Hero 영역 교체, info 상태 배지 스타일 추가, 국제화/UX 카드 신설 등(PRD 6장)
  • 다국어 카피(scan.aiPreparednessScore 등)도 재정리 필요
  • FAQ 스키마 생성 도구는 이번 스코프 밖으로 명시적으로 미룸 — 범위가 다시 늘어나지 않도록 별도 PRD/ADR에서 다룰 것

ADR-004 — 디자인 시스템: 토큰 기반 + data-theme 다크모드로 전환

상태Superseded by ADR-008 · 2026-08-13 — 디자인 시스템 페이지에 결과 반영

배경 (Context)

meta-scan-front 전 화면이 shadcn 기본 스캐폴드 토큰 위에, 실제로는 요소마다 theme === "dark" ? "..." : "..." 삼항 연산자로 cyan→purple→pink 그라디언트· backdrop-blur·glow 섀도우를 직접 나열하고 있었습니다("AI 생성 티"). 추가로 다음이 확인됐습니다:

  • components/ui/*(button/badge/tabs)는 이미 Tailwind dark: 클래스로 작성돼 있었는데, 이를 앱의 테마 쿠키(data-theme)와 연결하는 @custom-variant dark 선언이 주석 처리된 채 방치돼 OS prefers-color-scheme을 따르는 실제 버그였음
  • 점수/상태 색(cyan/purple/pink)이 등급과 무관하게 장식적으로만 쓰이고 있었음
  • 푸터의 SCANS: 247,891 조작된 통계, 에러 화면의 잘못된 문구 재사용 등 콘텐츠 버그가 동반돼 있었음

결정 (Decision)

  • 화이트/차콜 중립 + 인디고 단일 포인트 컬러로 토큰 재정의(globals.css), 라이트는 :root, 다크는 :root[data-theme="dark"]에 동일 변수명으로 선언
  • 주석 처리돼 있던 @custom-variant dark ([data-theme=dark])를 활성화 — components/ui/*와 나머지 화면의 다크모드 소스를 data-theme 쿠키 하나로 통일
  • 점수/상태 색을 success/warning/destructive 시맨틱 토큰으로 고정 매핑(score >= 80 ? success : score >= 60 ? warning : destructive)

ADR-003 — 유저 플로우 통합: 4-API 오케스트레이션 유지, 판정은 백엔드

상태Accepted · 2026-08-13, 2026-08-18 수정 (기획 인터뷰로 확정, 구현 착수 전 — PRD 페이지 3장에 결과 반영)

배경 (Context)

PRD가 제안한 TO-BE(단일 POST /api/v1/scan/analyze 엔드포인트로 4개 API 호출을 대체)와 실제 코드의 AS-IS(ProcessScreen이 4개 API를 병렬 호출하지만 응답을 버리고 /scan은 Math.random() 목업을 렌더) 사이에 다음 충돌/공백이 확인됐습니다:

  • /api/v1/scan/analyze 엔드포인트와 스코어링 엔진이 실제로는 존재하지 않음
  • AI 신호 추출 로직(구조화 데이터/prompts.txt/FAQ 등)이 백엔드 어디에도 없음
  • TO-BE가 전제하는 zustand 상태전달과 달리 scanStore.ts는 미사용 죽은 코드이고 /scan은 서버 컴포넌트
  • API 호출이 4개→1개로 줄면 ProcessScreen의 5단계 진행 UI가 실제 진행률을 반영할 수 없게 됨
  • 기존 4개 개별 API 함수가 단일 엔드포인트로 대체되면 사실상 미사용 코드가 될 상황

결정 (Decision)

  • 상태 전달은 PRD대로 zustand 스토어 — /scan을 클라이언트 컴포넌트로 전환하고 scanStore.ts를 재구현해 분석 결과(url → 원본 응답 + 점수)를 저장·조회
  • 단일 scanAnalyzeApi로 교체하지 않고, 기존 4개 API(robots/sitemap/ crawling/lighthouse) 호출을 그대로 유지 — ProcessScreen의 5단계 진행 애니메이션이 각 API의 실제 완료 시점에 반응하도록 하고 싶다는 요구가 우선했음
  • 각 API 완료마다 결과를 버리지 않고 저장, 4개가 다 모이면 프론트 유틸 (combineScanResults)이 이미 판정된 결과들을 취합 — 2026-08-18 수정: 최초엔 이 유틸이 점수까지 계산한다고 썼으나(computeAiPreparedness), 스코어링 자체가 ADR-005로 폐기됐고 사용자가 "판정은 백엔드, 프론트는 결과 취합만" 이라고 정정함. 그래서 판정(pass/warning/fail/info)은 전부 백엔드가 각 엔드포인트 응답의 checks[]에 담아 반환하고, 프론트는 그걸 그룹별로 합치고 summary (개수 집계)/topIssues(fail 우선 정렬)만 만듦 — "계산"이 아니라 "취합"
  • AI 신호의 원본 필드(구조화 데이터, prompts.txt, hreflang 등) 추출과 그 판정 모두 crawling API 응답 확장(백엔드) 몫 — 프론트는 추출도 판정도 하지 않음

고려한 대안 (Alternatives Considered)

대안기각 사유
PRD 원안: 신규 /analyze 단일 엔드포인트 + 서버 스코어링실시간 단계별 피드백(각 API 완료마다 UI 반영)을 유지하고 싶다는 요구와 맞지 않음 — 단일 호출은 완료 시점이 하나뿐이라 5단계 UI를 실제 진행률로 채울 수 없음
5단계 UI를 단일 로딩 인디케이터로 단순화애니메이션 자체는 유지하고 싶다는 요구가 있었음 — 대신 "가짜"가 아니라 실제 API 완료 이벤트에 반응하도록 개선하는 쪽을 택함
AI 신호/점수 계산을 위한 새 5번째 API(scanAiSignalsApi) 신설5단계 UI와 1:1로 깔끔하게 맞지만, crawling과 별도로 페이지를 한 번 더 로드해야 해서 Puppeteer 크롤링이 중복됨(PRD가 애초에 페이지를 두 번 안 읽으려고 getOnloadHtml 확장을 권장한 이유와 배치)
점수 계산을 crawling API 응답 확장과 함께 백엔드에서 처리기술적으로는 더 깔끔하지만, 지금 단계에서는 백엔드 변경 없이 빠르게 시작할 수 있는 프론트 계산 쪽을 우선하기로 함

결과 (Consequences)

얻은 것
  • PRD 원안보다 변경 범위가 작음 — 라우팅/오케스트레이션 구조를 갈아엎지 않고 "결과를 버리지 않게 고치기 + 점수 계산 얹기"로 축소됨
  • 진행 UI가 실제 이벤트 기반이 되어 사용자 신뢰도가 올라감(가짜 progress 제거)
  • 기존 4개 API가 계속 실사용되므로 "죽은 코드가 될 위험" 자체가 해소됨
트레이드오프
  • crawling 백엔드 확장은 여전히 필요 — 원본 신호 추출뿐 아니라 판정까지 백엔드 몫이라 작업량이 더 큼(2026-08-18 수정 반영)
  • prompts.txt 배치 방식, 캐시 도입 여부는 이번에 결정하지 않고 구현 시점으로 미룸(PRD 페이지 3.2 참고)
  • PRD 문서(5.2/6/7장)의 /analyze 엔드포인트 관련 서술은 이 ADR로 대체됨 — PRD 원문 자체는 아직 갱신하지 않았으므로 PRD md를 읽을 땐 이 ADR이 최신 결정임을 감안할 것

상태Accepted · 2026-08-13

  • 스테이지된 파일만 검사해 커밋 시 오버헤드가 적음

  • 이 시점 이전 커밋 히스토리는 형식이 소급 적용되지 않음

ADR-001 — 모노레포 의존성 관리 도구: pnpm workspaces

상태Accepted · 상세 원문은 docs/case-study/monorepo-dependency-management.md

배경 (Context)

meta-scan-api(Express + TypeScript, 원래 npm)와 meta-scan-front (Next.js, 원래 pnpm)를 git subtree로 packages/* 아래 합쳐 하나의 모노레포(meta-scan)로 구성하는 과정에서, 두 패키지가 서로 다른 패키지 매니저를 쓰고 있었기 때문에 워크스페이스 전체를 관리할 단일 도구가 필요했습니다. 후보는 pnpm workspaces와 Yarn Berry(Yarn 2+, PnP) 두 가지였습니다.

결정 (Decision)

  • 루트에 pnpm-workspace.yaml(packages/*)과 루트 package.json(packageManager: pnpm@10.15.0 고정 + 공통 스크립트) 추가
  • 패키지별 lockfile(meta-scan-api의 package-lock.json, meta-scan-front의 pnpm-lock.yaml)을 삭제하고 루트 pnpm-lock.yaml 하나로 통합
  • meta-scan-front의 package.json name이 루트와 같은 "meta-scan"이라 --filter 대상이 모호해지는 문제를 "meta-scan-front"로 변경해 해결
  • puppeteer/esbuild/sharp 등 네이티브 설치 스크립트가 있는 의존성은 루트 pnpm.onlyBuiltDependencies에 명시적으로 허용 등록(pnpm은 기본적으로 install script를 차단하기 때문)

비교 항목pnpm workspacesYarn Berry (PnP)

결과 (Consequences)

  • front 쪽 마이그레이션 비용 거의 없음(이미 pnpm 사용 중이었음)

  • Next.js 공식 지원 + 생태계 사례(Vite/Turborepo/Vue 등)가 pnpm 쪽에 풍부
트레이드오프
  • pnpm의 엄격한 phantom dependency 방지 때문에, 새 네이티브 의존성을 추가할 때마다 onlyBuiltDependencies에 수동으로 등록해야 함(안 하면 postinstall이 조용히 스킵됨)
  • 빌드 캐싱/파이프라인(Turborepo, Nx 등)은 아직 도입하지 않음 — 향후 고려 사항으로만 남아있음
