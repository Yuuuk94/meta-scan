ADR (설계 결정 기록)

왜 이렇게 만들었는지를 나중에 다시 찾아보기 쉽도록, 코드에 남지 않는 의사결정 배경을 기록합니다. 새 결정이 생기면 이 아래에 계속 추가하세요.

ADR-001 — 모노레포 의존성 관리 도구: pnpm workspaces

상태Accepted · 상세 원문은 docs/monorepo-dependency-management.md

배경 (Context)

meta-scan-api(Express + TypeScript, 원래 npm)와 meta-scan-front (Next.js, 원래 pnpm)를 git subtree로 packages/* 아래 합쳐 하나의 모노레포(meta-scan)로 구성하는 과정에서, 두 패키지가 서로 다른 패키지 매니저를 쓰고 있었기 때문에 워크스페이스 전체를 관리할 단일 도구가 필요했습니다. 후보는 pnpm workspaces와 Yarn Berry(Yarn 2+, PnP) 두 가지였습니다.

결정 (Decision)

  • 루트에 pnpm-workspace.yaml(packages/*)과 루트 package.json(packageManager: pnpm@10.15.0 고정 + 공통 스크립트) 추가
  • 패키지별 lockfile(meta-scan-api의 package-lock.json, meta-scan-front의 pnpm-lock.yaml)을 삭제하고 루트 pnpm-lock.yaml 하나로 통합
  • meta-scan-front의 package.json name이 루트와 같은 "meta-scan"이라 --filter 대상이 모호해지는 문제를 "meta-scan-front"로 변경해 해결
  • puppeteer/esbuild/sharp 등 네이티브 설치 스크립트가 있는 의존성은 루트 pnpm.onlyBuiltDependencies에 명시적으로 허용 등록(pnpm은 기본적으로 install script를 차단하기 때문)

고려한 대안 (Alternatives Considered)

비교 항목pnpm workspacesYarn Berry (PnP)
기존 상태와의 정합성front가 이미 pnpm 사용 중 → 마이그레이션 비용 최소front(pnpm→yarn), api(npm→yarn) 둘 다 전환 필요
네이티브 의존성 호환성puppeteer/lighthouse 같은 네이티브 바이너리와 문제 이력 적음PnP 모드에서 네이티브 addon과 호환성 이슈 이력 다수 — 실무에서 node-modules 모드로 우회하는 경우가 많음
Next.js 호환성공식 지원, 이슈 적음PnP 모드에서 과거 이슈 다수 리포트됨
학습/마이그레이션 비용낮음 — npm/yarn과 사용법 거의 동일상대적으로 높음 — .yarnrc.yml, zero-install, PnP 개념 학습 필요

전체 비교표와 마이그레이션 6단계는 docs/monorepo-dependency-management.md에 원문 그대로 있습니다.

결과 (Consequences)

얻은 것
  • front 쪽 마이그레이션 비용 거의 없음(이미 pnpm 사용 중이었음)
  • puppeteer/lighthouse 등 네이티브 의존성 관련 호환성 리스크 회피
  • Next.js 공식 지원 + 생태계 사례(Vite/Turborepo/Vue 등)가 pnpm 쪽에 풍부
트레이드오프
  • pnpm의 엄격한 phantom dependency 방지 때문에, 새 네이티브 의존성을 추가할 때마다 onlyBuiltDependencies에 수동으로 등록해야 함(안 하면 postinstall이 조용히 스킵됨)
  • 빌드 캐싱/파이프라인(Turborepo, Nx 등)은 아직 도입하지 않음 — 향후 고려 사항으로만 남아있음

ADR-002 — pre-commit/commit-msg 훅으로 린트·커밋 포맷 강제

상태Accepted · 2026-08-13

배경 (Context)

저장소를 스캔한 결과 테스트/CI/CD/브랜치 전략/커밋 컨벤션이 전무했고 (설계 페이지 2장 참고), 두 패키지의 ESLint 규칙 (@typescript-eslint/no-unused-vars, no-explicit-any 등)이 완전히 따로 관리돼 시간이 지날수록 규칙이 서로 어긋날 위험이 있었습니다.

결정 (Decision)

  • 루트에 husky(v9) + lint-staged + commitlint (@commitlint/config-conventional)를 devDependency로 추가
  • pre-commit: lint-staged가 스테이지된 파일만 골라 패키지별로 pnpm --filter <pkg> exec eslint --fix 실행
  • commit-msg: commitlint가 Conventional Commits 형식을 강제
  • 두 패키지가 겹치는 TypeScript 규칙만 eslint.config.base.mjs로 분리해 공유 (Next.js 전용 규칙 등 프레임워크 특화 부분은 각자 유지 — 설계 1.2/1.3 참고)

고려한 대안 (Alternatives Considered)

대안기각 사유
아무것도 안 함 (수동 규율에 의존)이미 컨벤션 부재가 확인된 상태 — 재발 가능성이 높다고 판단
simple-git-hooks 같은 더 가벼운 훅 러너더 가볍지만 lint-staged와의 조합 사례가 husky만큼 널리 쓰이지 않아, 앞으로 유지보수할 사람이 정보를 찾기 쉬운 쪽(husky)을 택함
로컬 훅 대신 GitHub Actions CI로 강제이 저장소엔 CI/CD 자체가 없고, 이번 스코프를 로컬 훅으로 한정함 — 서버 강제는 별도 ADR 대상
두 패키지 ESLint를 완전히 하나의 config로 통합meta-scan-front는 next/core-web-vitals 등 Next.js 전용 규칙이 필요해 100% 동일한 config는 기술적으로 맞지 않음 — 겹치는 규칙만 공유하는 절충안 채택

결과 (Consequences)

얻은 것
  • 커밋 로그가 파싱 가능한 형태로 통일 (향후 changelog 자동화 여지)
  • 스테이지된 파일만 검사해 커밋 시 오버헤드가 적음
  • 두 패키지의 미사용 변수/any 처리 규칙이 더 이상 따로 놀지 않음
트레이드오프
  • 새 devDependency 4종 추가(husky, lint-staged, commitlint 2종)
  • 로컬에서만 강제됨 — pnpm install을 안 하거나 --no-verify로 우회하면 그대로 통과됨(CI/CD 부재와 연결되는 한계)
  • 이 시점 이전 커밋 히스토리는 형식이 소급 적용되지 않음
