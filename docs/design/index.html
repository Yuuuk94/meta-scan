1.1 저장소 구조

pnpm workspace 모노레포입니다. 두 패키지는 각자 원래 독립 저장소였고 git subtree로 합쳐져 원본 커밋 히스토리를 그대로 보존하고 있습니다(docs/monorepo-dependency-management.md, 선택 배경은 ADR-001 참고). 풀스택 프레임워크 하나로 합쳐진 구조가 아니라, 프레임워크 자체가 다른 두 앱(Express / Next.js)이 나란히 존재하는 구조입니다.

프론트 진입점단일 파일 없음 — src/middleware.ts(로케일 리다이렉트) + src/app/[lang]/layout.tsx(루트 레이아웃)가 사실상의 진입점
패키지 간 연결런타임 의존 없음(둘 다 독립 배포) — 프론트가 NEXT_PUBLIC_META_SCAN_API로 API를 HTTP 호출만 함

항목확인된 패턴

API 설계 패턴

메서드/경로모듈응답 포맷
GET /api/v1/healthzhealth{status:"ok"}
POST /api/v1/scan/pingscan{status:"ok", ...result}
POST /api/v1/scan/robotsTxtscan{status:"ok", ...result}
POST /api/v1/scan/siteMapscan{status:"ok", ...result}
POST /api/v1/scan/crawlingscan{status:"ok", ...MetaScanResult}
POST /api/v1/lighthouse/runlighthouse불일치 — format==="html"이면 raw HTML, 아니면 lhr 객체를 statusOk 없이 그대로 반환

REST 스타일, 라우트 네이밍은 /api/v1/<모듈키>/<액션>(app.ts의 routers 맵 기반). 조회성 액션(ping/robotsTxt/siteMap/crawling)도 전부 POST를 쓰고 GET은 healthz 하나뿐입니다. 응답 포맷은 모듈 간 완전히 통일돼 있지 않습니다(위 표 참고).

DB / ORM

없음 (확인됨) — package.json에 prisma/mongoose/typeorm/pg 등 DB 관련 의존성이 전무합니다. 매 요청을 즉시 스캔해 응답하는 완전 무상태(stateless) API이며, 영속 저장소 자체가 없습니다. 마이그레이션 방식도 해당 없음.

인증 / 인가

없음 (확인됨) — jsonwebtoken/passport/next-auth 등 인증 관련 의존성이 없고, 별도 인증 미들웨어도 없습니다. 모든 엔드포인트가 완전 퍼블릭입니다.

2. 공통 영역 CROSS-CUTTING

영역확인된 사실
테스트 프레임워크없음 — jest/vitest/playwright 등 의존성 없음, *.test.*/*.spec.* 파일 0건. 두 패키지 CLAUDE.md에도 "테스트 러너가 있다고 가정하지 말 것"이라 명시됨
Git 브랜치 전략현재 origin에 main 단일 브랜치만 존재. subtree 병합 이전 원본 히스토리엔 dev 브랜치 → PR 병합 흔적이 남아있지만, 통합 저장소 기준 별도 전략 문서나 규칙은 없음
Git 훅있음 — husky. pre-commit에서 lint-staged가 스테이지된 파일만 패키지별 ESLint --fix, commit-msg에서 commitlint가 커밋 메시지 형식을 검사. pnpm install 시 prepare 스크립트로 자동 활성화 (ADR-002 참고)
커밋 메시지 컨벤션있음 — Conventional Commits(<type>(<scope>)?: <subject>)를 commitlint로 강제. 단, 이 훅 도입(2026-08) 이전 히스토리("fix cors", "update" 등 자유 형식)는 그대로 남아있고 소급 적용되지 않음
CI/CD없음 — .github/workflows 등 전무, 원격(서버) 검사 파이프라인 없음. 위 Git 훅은 로컬에서만 강제되고 서버 쪽 강제 장치는 아님. Docker 빌드도 pnpm docker:build:api 수동 커맨드로만 존재
