# `deploy` 스킬 — main 배포 + 이슈 정리

> **상태**: 2026-09-08, 사용자와의 순차 인터뷰로 확정. `.claude/skills/deploy/SKILL.md`(런북)까지
> 실제로 만듦. 아직 실제 release/hotfix로 시범 실행은 안 해봄.

## 배경

`docs/harness/tdd-issue-loop.md`의 TDD 이슈 루프는 PR을 여는 데서 끝나고 절대 머지하지 않는다
(사람이 서버 직접 확인 후 승인). 그런데 실제로 이슈 #44(root pingApi 콜드스타트 hotfix)를 처리하며
"PR 머지 → dev 백머지 → 관련 이슈 정리"를 매번 손으로 했고(그 과정에서 `status:done`인데 계속
열려있던 이슈 18개를 한꺼번에 발견해 정리하기도 함), 이 반복 작업을 스킬로 만들자는 요청에서
시작됨.

## tdd-issue-loop과의 경계

- **tdd-issue-loop**: 이슈 등록(또는 대화 중 요청 접수)부터 PR 오픈까지. `main`을 절대 건드리지
  않음.
- **deploy**: PR이 열린 다음부터 — 실제로 `main`에 머지하고, `dev`로 백머지하고, 이슈를 닫는 것까지.
  `dev`/`feat/*`는 절대 만들지 않음(이미 tdd-issue-loop이 만든 걸 가져다 쓸 뿐).

이 경계를 정할 때 처음엔 "이슈 등록부터 머지까지 다 하는 새 스킬(B)"을 따로 만들려고 했으나,
인터뷰 중 "B가 결국 tdd-issue-loop이랑 거의 같아진다"는 게 드러나서 B는 별도로 안 만들고
tdd-issue-loop을 확장하는 쪽으로 정리됨(대화 시작점 지원 + PR 이후 검증 강화). 남은 진짜 새
스킬이 이 `deploy`.

## 확정된 결정 사항 (2026-09-08 인터뷰)

| 항목 | 결정 | 비고 |
|---|---|---|
| 스코프 | **release/hotfix 둘 다 하나의 스킬** | "브랜치가 중요한 게 아니라 main으로 병합하는 행위가 제일 중요하다"(사용자) — 입력(이미 열린 hotfix PR vs dev에 쌓인 미배포 작업)에 따라 스킬 내부에서 분기하되, 사람에게는 하나의 "배포해줘" 진입점. |
| 호출 방식 | **main을 바라보는 열린 PR 자동 탐지** (PR 번호 수동 지정 아님) | 여러 개 열려있으면 사람에게 물어봄. 없으면 `dev`가 `main`보다 앞서 있는지 확인해서 release 경로로 전환. |
| release 브랜치 생성 주체 | **deploy 스킬이 직접 `release/x.y.z` 브랜치+PR까지** | 사람이 미리 만들어두는 방식도 고려했으나, "C가 브랜치 생성+PR까지"로 확정 — 배포 스킬 호출 = 그 시점 dev의 미배포 작업을 릴리즈하겠다는 의도로 취급. |
| 버전 범프 | **deploy 스킬이 처리, 단 버전 숫자는 사람이 지정** | 처음엔 "버전 범프는 스킬 스코프 밖, 사람이 직접"으로 갔다가, release 브랜치를 스킬이 직접 판다는 게 확정되면서 재조정("알아서 할게" — 위임받음) — 브랜치를 팔 때 버전 범프 커밋이 안 들어가면 릴리즈 브랜치의 의미가 없어서, 스킬이 3개 package.json을 동시에 범프하는 커밋까지 만듦. 단 몇으로 올릴지(semver 판단)는 여전히 사람이 정함. |
| 태그 | **안 씀** | "태그 현재 안 씀"(사용자) — `git-branching-strategy.md`의 이상적 다이어그램(`main ──► release ──► main (tag)`)과 다르게, 실제로는 태그를 만들지 않는 쪽으로 확정. |
| 머지 승인 | **매번 명시적 컨펌 후 머지** | 이 저장소의 "승인 없는 commit/push 금지" 원칙을 배포 스킬에도 그대로 적용 — 스킬 호출 자체를 암묵적 승인으로 취급하지 않고, 실제 머지 직전에 한 번 더 확인. |
| 백머지 | **hotfix/release 공통, 매번 자동** | main 머지 직후 `main`→`dev` 백머지까지 deploy 스킬이 그 자리에서 처리 — hotfix는 정의상(`git-branching-strategy.md`) 필수, release도 브랜치 자체 커밋(버전 범프)이 dev에 반영돼야 하므로 동일 적용. |
| 이슈 정리 | **`status:done`이면서 `main`의 조상인 이슈 전부 close, hotfix/release 공통 일반화** | 2026-09-08에 실제로 손으로 했던 방식(`status:done` 라벨 + `main`에 이미 배포된 것 전부 일괄 close)을 그대로 스킬 로직화. PR 본문의 `Closes #N` 자동 클로즈(hotfix가 main으로 직행할 때 발동)와 겹쳐도 안전(멱등) — 겹치는 건 문제 아님. |

## 열린 질문 / 후속 과제

- 릴리즈 캐덴스(언제 release를 만들지 — 정기 vs 기능 단위)는 여전히 미정
  (`git-branching-strategy.md` 참고) — deploy 스킬은 "호출되면 그 시점 기준으로 배포"할 뿐, 언제
  호출할지는 계속 사람이 판단.
- 세마버 범프 레벨(patch/minor/major) 자동 판단은 스코프 밖으로 명시적으로 뺌 — 사람이 숫자를
  직접 지정.
- 실제 release/hotfix로 아직 시범 실행 안 함 — 다음 배포 때 실제로 돌려보고 스킬 내용을 검증.
