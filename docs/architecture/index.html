1.1 저장소 구조

pnpm workspace 모노레포입니다. 두 패키지는 각자 원래 독립 저장소였고 git subtree로 합쳐져 원본 커밋 히스토리를 그대로 보존하고 있습니다(docs/case-study/monorepo-dependency-management.md, 선택 배경은 ADR-001 참고). 풀스택 프레임워크 하나로 합쳐진 구조가 아니라, 프레임워크 자체가 다른 두 앱(Express / Next.js)이 나란히 존재하는 구조입니다.

컴포넌트 구현 패턴

항목확인된 패턴
파일당 컴포넌트 수1개가 원칙(컴포넌트명과 파일명 1:1). 예외: shadcn 유래 프리미티브(Accordion.tsx, Tabs.tsx)는 컴파운드 컴포넌트라 서브 컴포넌트 여럿을 한 파일에 둠
export 방식ui/atoms/ui/molecules의 shadcn 유래 프리미티브(Badge, Button, Input, Card, Accordion, Tabs)는 function X() {} 선언 후 파일 하단에서 named export. 그 외는 아래 "선언 방식" 참고. 예외: page.tsx/layout.tsx는 Next.js 규약상 default export
선언 방식 (화살표 vs function)둘로 갈림 — ui/organisms/의 프레젠테이션 컴포넌트(HeroSection, FAQSection, ProcessSection, RootHeader, RootFooter, ServiceStatus)와 ui/molecules/ToggleSetting.tsx·ProcessStep.tsx·ui/atoms/Loading.tsx는 export const X = (props) => {}. 화면 전환 컴포넌트(ProcessScreen, ErrorScreen, ADR-006용으로 신설된 BlockedScreen)는 export function X(props) {}
클래스형 컴포넌트없음
props 전달 방식Context 없이 theme/lang(+ t 사전 객체)을 모든 하위 컴포넌트에 계속 내려주는 props drilling. 공통 타입은 DefaultProps/DefaultPageProps — ADR-010 이후에도 안 바뀜
UI 프리미티브 골격ui/atoms/*·ui/molecules/*: cva variant 정의 → cn()(utils/cn.ts, clsx+tailwind-merge)로 className 병합 → data-slot 속성 → named export. 디자인 시스템 §를 가리키는 JSDoc 주석이 붙어있는 경우가 많음(예: Rule.tsx가 §5, StatusBadge.tsx가 §2/§8) — 디자인 시스템 페이지 5절 참고

API 호출 패턴

api/instance.ts(구 apis/index.ts)가 axios.create({ baseURL: NEXT_PUBLIC_META_SCAN_API })로 공유 인스턴스를 만들고, api/scanApi.ts(scanRobotsTxtApi/scanSiteMapApi/ scanCrawlingApi/lsRunApi)와 api/statusApi.ts (pingApi — 구 sitePingApi)가 이 위에서 엔드포인트별 함수를 노출합니다. 호출 방식은 컨텍스트별로 다릅니다: 서버 컴포넌트는 단건 await로 직접 호출해 try/catch로 에러를 잡고, ProcessScreen(클라이언트)은 여러 API를 Promise.allSettled로 병렬 호출해 .then/.catch로 각각 처리합니다.

baseURL 불일치는 해결됨 — 이전엔 sitePingApi만 인스턴스의 baseURL을 쓰고 나머지 scan*Api 함수들은 NEXT_PUBLIC_META_SCAN_API를 경로 앞에 다시 붙이던 불일치가 있었는데, fix(front): drop redundant baseURL concat in scanApi.ts 커밋으로 지금은 전부 baseURL만 씁니다. API 함수 내부에 공통 에러 핸들러(인터셉터)는 여전히 없고, 에러 처리는 항상 호출부 책임입니다.
가장 중요한 확인 사실 — 파이프가 아직 안 이어져 있음. ADR-010 마이그레이션이 새로 만든 services/combineScanResults.ts(4개 스캔 응답을 그룹별로 취합 — 계산 아님, ADR-003 참고)와 services/scanGating.ts (ADR-006 robots.txt 게이팅 로직)는 둘 다 파일에 함수 시그니처만 주석으로 적힌 export {} 스텁이고, ProcessScreen은 여전히 4개 API를 병렬 호출은 하지만 응답 바디를 저장하지 않고 status === "ok"만 확인한 뒤 버립니다. /scan 결과 페이지(app/[lang]/scan/page.tsx)도 여전히 서버 컴포넌트 안에서 Math.random()으로 만든 목업을 렌더링합니다. 즉 "이미 있는 UI/API 사이에 파이프를 연결"하는 작업이 아직 이 마이그레이션 이후로도 남아있습니다 — 루트 CLAUDE.md "현재 상태" 절과 동일한 사실입니다.

hooks/와 ui/templates/도 같은 이유로 아직 빈 자리입니다 — hooks/는 React Query(@tanstack/react-query, 아직 미설치)를 감쌀 클라이언트 훅 자리이고, ui/templates/는 라우트별 organisms 조립 스켈레톤 자리인데, 지금은 app/[lang]/**/page.tsx가 여전히 ui/organisms/를 직접 조립합니다.

레이어 구조

2026-08-21, ADR-011에 따라 Hexagonal(Ports & Adapters) 3계층으로 마이그레이션 — domain/(포트 인터페이스) / application/(유스케이스) / adapters/(inbound: HTTP 컨트롤러·라우터, outbound: 브라우저 자동화 어댑터)로 재구성됐습니다. 이전 src/modules/* 레이어드 구조(scan/lighthouse/health 모듈별 폴더)는 대체됐습니다. entities 계층은 만들지 않았습니다 — PRD 체크리스트 명세를 확인한 뒤 이 프로젝트엔 불필요하다고 판단한 것으로 기록돼 있습니다. 경로 별칭도 이전엔 @core/*/@constant/*/@config/*/ @infra/*/@modules/* 5개였는데, 같은 시점에 프론트와 동일하게 @/* 하나로 통합됐습니다.

REST 스타일, 라우트 네이밍은 /api/v1/<모듈키>/<액션>(app.ts의 routers 맵 기반). 조회성 액션(ping/robotsTxt/siteMap/crawling)도 전부 POST를 쓰고 GET은 healthz 하나뿐입니다. 응답 포맷은 모듈 간 완전히 통일돼 있지 않습니다(위 표 참고).

DB / ORM

없음 (확인됨) — package.json에 prisma/mongoose/typeorm/pg 등 DB 관련 의존성이 전무합니다. 매 요청을 즉시 스캔해 응답하는 완전 무상태(stateless) API이며, 영속 저장소 자체가 없습니다. 마이그레이션 방식도 해당 없음.

인증 / 인가

없음 (확인됨) — jsonwebtoken/passport/next-auth 등 인증 관련 의존성이 없고, 별도 인증 미들웨어도 없습니다. 모든 엔드포인트가 완전 퍼블릭입니다.

에러 핸들링 & 로깅

서비스 메서드에서 try/catch로 ApiError.internal()을 던지면(원본 에러는 대부분 로깅 없이 삼켜짐) 컨트롤러의 this.handle() 래퍼가 next(err)로 전달하고, 존재하지 않는 라우트는 notFound 미들웨어가 next(ApiError.notFound())를 호출합니다. 둘 다 최종적으로 errorHandler 미들웨어에서 res.status(status).json({ error: message })로 응답하며, NODE_ENV=development일 때만 stack을 포함합니다.

2. 공통 영역 CROSS-CUTTING

영역확인된 사실
테스트 프레임워크결정됨, 미도입 — ADR-012(2026-08-24)로 meta-scan-front는 Jest, meta-scan-api는 Vitest로 패키지별로 다르게 채택 확정. 실제 devDependency 추가·설정 파일 작성은 아직 안 됨 — docs/harness/tdd-issue-loop.md의 이슈 기반 TDD 파이프라인이 처음 도입하게 될 예정
Git 브랜치 전략있음 — Full Git Flow. main(프로덕션) – dev(통합/스테이징) – feat/* 3단에서, release/*·hotfix/*까지 더한 원조 Git Flow(Vincent Driessen)로 2026-08 확장(docs/case-study/git-branching-strategy.md). CI 자동화 없이 수동 운영이라 release 완료 시 main+dev 양방향 백머지를 사람이 챙겨야 하는 게 알려진 약점
Git 훅있음 — husky. pre-commit에서 lint-staged가 스테이지된 파일만 패키지별 ESLint --fix, commit-msg에서 commitlint가 커밋 메시지 형식을 검사. pnpm install 시 prepare 스크립트로 자동 활성화 (ADR-002 참고)
커밋 메시지 컨벤션있음 — Conventional Commits(<type>(<scope>)?: <subject>)를 commitlint로 강제. 단, 이 훅 도입(2026-08) 이전 히스토리("fix cors", "update" 등 자유 형식)는 그대로 남아있고 소급 적용되지 않음
CI/CD없음 — .github/workflows 등 전무, 원격(서버) 검사 파이프라인 없음. 위 Git 훅은 로컬에서만 강제되고 서버 쪽 강제 장치는 아님. Docker 빌드도 pnpm docker:build:api 수동 커맨드로만 존재. GitHub Pages(docs/, main 브랜치 소스)만 예외적으로 자동 배포됨
Claude Code 개발 하네스있음 — .claude/agents/·.claude/skills/에 파이프라인형 서브에이전트 구성. design-intake → publish-front → qa-front-publish(디자인 반영), dev-interview → dev-backend/dev-front → qa-backend/qa-front(GitHub Issues 기반 TDD 루프, docs/harness/tdd-issue-loop.md), blog-writer(케이스 스터디 → 블로그 초안) 등. 로드맵/미도입 항목은 docs/harness/dev-lifecycle-harness.md 참고
