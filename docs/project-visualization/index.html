meta-scan 프로젝트 시각화

저장소를 직접 스캔해 확인한 사실만 정리했습니다. 확신이 없거나 코드에서 근거를 찾지 못한 항목은 확인 필요로 표시했습니다.

1. 프로젝트 컨셉 · 기획 의도 CONCEPT

meta-scan은 URL 하나를 입력받아 메타 태그 · robots.txt · sitemap · Lighthouse(성능/SEO/접근성/모범사례)를 스캔해 보여주는 사이트 진단 서비스입니다. 여기서 한 걸음 더 나아가, Lighthouse가 다루지 않는 "AI 시대의 발견 가능성" — 구조화 데이터, prompts.txt 같은 AI 신호, 인용 친화성(GEO), AEO(AI 엔진 최적화) 준비도 — 까지 0–100점 하나의 점수로 합산해 보여주는 "Lighthouse+ / AI Preparedness" 제품으로 확장하는 중입니다.

왜 만드는가

기존 Lighthouse는 사람이 브라우저로 방문했을 때의 성능/접근성/SEO 기본기를 측정하지만, ChatGPT나 Perplexity 같은 AI 답변 엔진이 이 사이트를 실제로 인용할 수 있는지는 측정하지 않습니다. meta-scan 은 이 공백 — 구조화 데이터 유무, AI가 참고할 수 있는 명시적 신호, 본문이 인용하기 좋은 형태로 구조화됐는지 — 를 기존 SEO 점검과 같은 자리에서 함께 보여주는 것을 목표로 합니다.

2. 기획 · PRD PLANNING

저장소에 존재하는 기획 문서는 docs/meta-scan-plus-prd.md 하나뿐입니다. 별도의 "기획서"나 "유저플로우" 파일은 없고, 유저 플로우도 이 PRD 안에 짧게 포함돼 있습니다.

2.1 현재 구현 상태

영역상태비고

분석 진행 화면UI만 구현API 응답을 저장하지 않고 버림 (ProcessScreen.tsx)

2.2 목표

  • 기존 Lighthouse 결과 + AI 친화도(AEO 준비도) 0–100 점수 제공
  • 구조화 데이터 · 프롬프트 신호 · 인용 친화성 등 Lighthouse가 다루지 않는 영역을 룰 기반으로 보강
  • 이미 만들어진 /scan 리포트 화면에 실제 분석 결과 연결
  • 외부 ML/유료 API 없이 기존 Puppeteer + 자체 파싱만으로 구현 (신규 라이브러리 추가 없음)

  • JSON-LD 파싱 에러 −6

  • 결과 캐시의 영속화(현재 무상태 API라 재시작 시 캐시 소실 — DB 도입 시점에 재검토)
  • PDF 리포트, 경쟁 URL 비교(최대 3개)

4.1 저장소 구조

pnpm workspace 모노레포입니다. 두 패키지는 각자 원래 독립 저장소였고 git subtree로 합쳐져 원본 커밋 히스토리를 그대로 보존하고 있습니다(docs/monorepo-dependency-management.md). 풀스택 프레임워크 하나로 합쳐진 구조가 아니라, 프레임워크 자체가 다른 두 앱(Express / Next.js)이 나란히 존재하는 구조입니다.

REST 스타일, 라우트 네이밍은 /api/v1/<모듈키>/<액션>(app.ts의 routers 맵 기반). 조회성 액션(ping/robotsTxt/siteMap/crawling)도 전부 POST를 쓰고 GET은 healthz 하나뿐입니다. 응답 포맷은 모듈 간 완전히 통일돼 있지 않습니다(위 표 참고).

DB / ORM

없음 (확인됨) — package.json에 prisma/mongoose/typeorm/pg 등 DB 관련 의존성이 전무합니다. 매 요청을 즉시 스캔해 응답하는 완전 무상태(stateless) API이며, 영속 저장소 자체가 없습니다. 마이그레이션 방식도 해당 없음.

인증 / 인가

없음 (확인됨) — jsonwebtoken/passport/next-auth 등 인증 관련 의존성이 없고, 별도 인증 미들웨어도 없습니다. 모든 엔드포인트가 완전 퍼블릭입니다.

5. 공통 영역 CROSS-CUTTING

영역확인된 사실
테스트 프레임워크없음 — jest/vitest/playwright 등 의존성 없음, *.test.*/*.spec.* 파일 0건. 두 패키지 CLAUDE.md에도 "테스트 러너가 있다고 가정하지 말 것"이라 명시됨
Git 브랜치 전략현재 origin에 main 단일 브랜치만 존재. subtree 병합 이전 원본 히스토리엔 dev 브랜치 → PR 병합 흔적이 남아있지만, 통합 저장소 기준 별도 전략 문서나 규칙은 없음
커밋 메시지 컨벤션Conventional Commits(feat:/fix:) 아님. 예: "Add mermaid-diagram skill...", "fix cors", "update", "remove animate" — 자유 영문 명령형이 섞여 있고 강제 도구(commitlint/husky)도 없음
CI/CD없음 — .github/workflows 등 전무, lint/build/test 자동 파이프라인 없음. Docker 빌드도 pnpm docker:build:api 수동 커맨드로만 존재
