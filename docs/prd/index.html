meta-scan PRD · 기획

저장소를 직접 스캔해 확인한 사실만 정리했습니다. 확신이 없거나 코드에서 근거를 찾지 못한 항목은 확인 필요로 표시했습니다.

1. 프로젝트 컨셉 · 기획 의도 CONCEPT

meta-scan은 URL 하나를 입력받아 메타 태그 · robots.txt · sitemap · Lighthouse(성능/SEO/접근성/모범사례)를 스캔해 보여주는 사이트 진단 서비스입니다. 여기서 한 걸음 더 나아가, Lighthouse가 다루지 않는 "AI 시대의 발견 가능성" — 구조화 데이터, prompts.txt 같은 AI 신호, 인용 친화성(GEO), AEO(AI 엔진 최적화) 준비도 — 도 항목별로 점검해 pass / warning / fail / info로 보여주는 SEO/AEO 체크리스트 제품입니다. 수익 모델은 Google 애드센스(무료 도구 + 광고 트래픽)입니다.
2026-08-18 방향 정정 — 이전 버전(v1)은 이 신호들을 0–100점 하나로 가중합산하는 "AI Preparedness Index" 스코어링 엔진으로 기획됐었습니다. 이건 사용자 본인이 낸 기획이 아니라 이전 세션에서 AI가 덧붙인 것으로 확인되어 폐기했습니다. 원래 기획 의도는 점수를 매기는 능동적 진단이 아니라, 체크리스트를 보여주는 수동적 진단 도구였고 — 수익 모델(애드센스: 무료·고트래픽·광고 기반)도 점수 합산형 프리미엄 제품과는 문법이 맞지 않았습니다. 최신 근거는 docs/meta-scan-plus-prd.md.

왜 만드는가

기존 Lighthouse는 사람이 브라우저로 방문했을 때의 성능/접근성/SEO 기본기를 측정하지만, ChatGPT나 Perplexity 같은 AI 답변 엔진이 이 사이트를 실제로 인용할 수 있는지는 측정하지 않습니다. meta-scan 은 이 공백 — 구조화 데이터 유무, AI가 참고할 수 있는 명시적 신호, 본문이 인용하기 좋은 형태로 구조화됐는지 — 를 기존 SEO 점검과 같은 자리에서 항목별 체크리스트로 함께 보여주는 것을 목표로 합니다.

제품 컨셉

URL 1개를 입력하면 두 영역이 함께 점검됩니다: 기존 스캔 영역(메타 태그· robots/sitemap·Lighthouse — Lighthouse 4개 점수는 구글 자체 채점이라 숫자 그대로 유지)과 신규 확장 영역(구조화 데이터·AI 신호(prompts.txt 등)·인용 친화성·색인/미리보기· 국제화/UX). 신규 확장 영역의 각 항목은 pass/warning/fail/info로만 판정되고, 합산 점수나 등급은 만들지 않습니다. 결과 화면 Hero는 점수 대신 가장 심각한 실패 항목 상위 N개를 보여줍니다.

제품 방향의 일관성 — 같은 기획 세션에서 "TubeBuddy를 레퍼런스로 한 YouTube SEO SaaS 피벗"이 잠시 제안됐다가 중단된 이력이 있습니다. 현재 컨셉은 그 피벗과 무관하게, 웹사이트 SEO/AEO 체크리스트라는 원래 방향을 그대로 유지하고 있습니다.

2. 기획 · PRD PLANNING

저장소에 존재하는 기획 문서는 docs/meta-scan-plus-prd.md 하나뿐입니다. 별도의 "기획서"나 "유저플로우" 파일은 없고, 유저 플로우도 이 PRD 안에 짧게 포함돼 있습니다.

2.2 목표

  • 기존 Lighthouse 4개 점수(성능/SEO/접근성/모범사례)는 숫자 그대로 유지
  • 구조화 데이터 · 프롬프트 신호 · 인용 친화성 등 Lighthouse가 다루지 않는 영역을 개별 체크리스트 항목(pass/warning/fail/info)으로 룰 기반 판정 — 합산 점수 없음
  • 이미 만들어진 /scan 리포트 화면에 실제 체크리스트 결과 연결, 합산 점수 Hero는 "가장 심각한 실패 항목 N개" 강조 영역으로 교체
  • 외부 ML/유료 API 없이 기존 Puppeteer + 자체 파싱만으로 구현 (신규 라이브러리 추가 없음)
  • 애드센스 승인/운영 고려 — 결과 화면은 로그인 없이 공개 접근, 항목별 설명 텍스트로 원본 콘텐츠 확보

2.3 체크리스트 그룹 · 판정 규칙 (스코어링 아님)

각 항목은 가중치 없이 아래 기준대로 pass / warning / fail / info 넷 중 하나로만 판정합니다. 합산 점수·등급·가중치는 없습니다. ADR-003에 따라 이 판정은 백엔드가 아니라 프론트 유틸 (computeChecklist)이 4개 API 응답을 모은 뒤 클라이언트에서 계산합니다.

그룹항목 예시판정 감각
색인(Indexing)robots 허용, canonical 다중 태그, noindex 여부대부분 pass/fail — 검색엔진 노출에 직결
미리보기(Previews)OG/Twitter 필수값, og:image 크기 메타, favicon누락 시 대부분 warning
AI 신호(AI Signals)prompts.txt, PromptObject, FAQ 섹션, 구조화 데이터 타입없어도 감점 아님 — "있으면 좋은 신호"로 info 표시
콘텐츠(Content)본문 단어 수, 헤딩 계층, TL;DR임계치 기준 pass/warning
국제화/UXhreflang, viewportviewport는 warning, hreflang은 info
Lighthouseperformance/seo/accessibility/best-practices구글 자체 점수, 체크리스트 판정 대상 아님

Hero 영역에는 개수 요약 대신 fail 항목 상위 N개(기본 3개, 모자라면 warning으로 채움)를 그대로 노출합니다 — "점수가 낮습니다" 대신 "지금 고쳐야 할 것". 세부 규칙과 각 그룹 표는 docs/meta-scan-plus-prd.md 3~4절 참고.

2.4 이번 스코프에서 의도적으로 뺀 것 (v0.2 후보)

  • og:image 실제 픽셀 크기 측정(이미지 다운로드/디코딩)
  • sitemap.xml 내 URL 개수 카운트(GET + XML 파싱)
  • 애드센스 실제 슬롯 삽입, 광고 정책 준수 세부 작업
  • PDF 리포트, 경쟁 URL 비교(최대 3개)

2.5 다음 단계 (이 PRD 범위 밖) — qna.json 생성 도구

체크리스트 도구가 완성된 뒤 이어서 만들 계획입니다. 체크리스트가 "이 사이트엔 FAQ/PromptObject 신호가 없다"고 진단해주면, 후속 도구는 실제 페이지 콘텐츠를 기반으로 qna.json(질문-답변 쌍, prompts.txt/FAQPage 계열 포맷)을 생성해 처방까지 이어줍니다. 2.3절 AI 신호 그룹의 감지 로직(구조화 데이터 타입, FAQ 섹션)이 그대로 입력 데이터로 재사용될 가능성이 높습니다.

3. 유저 플로우 FLOW

원래는 AS-IS(현재 코드)와 TO-BE(PRD 원안)를 별도 다이어그램 두 개로 그렸으나, 기획 인터뷰를 거쳐 단일 목표 플로우로 통합했습니다. 결정 배경과 검토한 대안은 ADR-003에 있습니다.

백엔드 변경 필요 지점 — crawling API 응답 확장(구조화 데이터, prompts.txt, FAQ 섹션, hreflang, viewport, noindex, 본문 단어수/h2·h3, TL;DR 후보 등 AI 신호 원본 필드, PRD 3장 그대로)이 선행돼야 프론트 판정이 의미가 있습니다. "프론트에서 판정한다"는 결정이 "백엔드 작업이 없다"는 뜻은 아닙니다 — 원본 신호 추출은 여전히 백엔드(Puppeteer DOM 접근) 몫입니다. prompts.txt는 DOM이 필요 없는 순수 fetch라 별도 API로 빼지 않고 crawling이 원본 HTML을 가져오는 지점에서 병렬 fetch로 함께 처리 — 5번째 API 호출을 만들면 ProcessScreen의 4단계 구성이 깨지기 때문(ADR-003이 5번째 API 대안을 기각한 이유와 동일).

3.2 이번엔 결정하지 않은 세부사항

  • 동일 URL 캐시 도입 여부 — 프론트 계산이라 서버 캐시의 실익이 크지 않아 이번 스코프에서는 보류

3.1은 2026-08-13 기획 인터뷰로 확정된 목표 상태이며, 아직 코드에는 반영되지 않았습니다.
