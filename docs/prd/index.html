meta-scan PRD · 기획

저장소를 직접 스캔해 확인한 사실만 정리했습니다. 확신이 없거나 코드에서 근거를 찾지 못한 항목은 확인 필요로 표시했습니다.

1. 프로젝트 컨셉 · 기획 의도 CONCEPT

meta-scan은 URL 하나를 입력받아 메타 태그 · robots.txt · sitemap · Lighthouse(성능/SEO/접근성/모범사례)를 스캔해 보여주는 사이트 진단 서비스입니다. 여기서 한 걸음 더 나아가, Lighthouse가 다루지 않는 "AI 시대의 발견 가능성" — 구조화 데이터, prompts.txt 같은 AI 신호, 인용 친화성(GEO), AEO(AI 엔진 최적화) 준비도 — 까지 0–100점 하나의 점수로 합산해 보여주는 "Lighthouse+ / AI Preparedness" 제품으로 확장하는 중입니다.

왜 만드는가

기존 Lighthouse는 사람이 브라우저로 방문했을 때의 성능/접근성/SEO 기본기를 측정하지만, ChatGPT나 Perplexity 같은 AI 답변 엔진이 이 사이트를 실제로 인용할 수 있는지는 측정하지 않습니다. meta-scan 은 이 공백 — 구조화 데이터 유무, AI가 참고할 수 있는 명시적 신호, 본문이 인용하기 좋은 형태로 구조화됐는지 — 를 기존 SEO 점검과 같은 자리에서 함께 보여주는 것을 목표로 합니다.

제품 컨셉 다이어그램

제품 방향의 일관성 — 같은 기획 세션에서 "TubeBuddy를 레퍼런스로 한 YouTube SEO SaaS 피벗"이 잠시 제안됐다가 중단된 이력이 있습니다. 현재 컨셉은 그 피벗과 무관하게, 웹사이트 SEO/AEO 스캐너라는 원래 방향을 그대로 유지하고 있습니다.

2. 기획 · PRD PLANNING

저장소에 존재하는 기획 문서는 docs/meta-scan-plus-prd.md 하나뿐입니다. 별도의 "기획서"나 "유저플로우" 파일은 없고, 유저 플로우도 이 PRD 안에 짧게 포함돼 있습니다.

2.1 현재 구현 상태

영역상태비고
크롤링 인프라 (Puppeteer 로드 + DOM 추출)구현됨scanService.getOnloadHtml
기본 메타 추출 (title/description/og/twitter/img alt 등)구현됨scanService.crawling → runChecks
robots.txt 파싱 + allow 판정구현됨scanService.robotsTxt (자체 파서)
sitemap.xml 존재 확인 (HEAD)일부 구현URL 개수 카운트는 미구현
Lighthouse 점수 (performance/seo/a11y/best-practices)구현됨LighthouseService + chrome-launcher
AI 친화도(AEO) 점수 · 구조화 데이터 · prompts.txt · hreflang/viewport미구현백엔드에 관련 코드 없음 — crawling 응답 확장으로 추가 예정(3장 목표 플로우)
스코어링 엔진(0–100 가중합산)미구현점수 계산 로직 전무 — 목표안은 프론트 유틸로 계산(3장, ADR-003)
결과 통합 API (/api/analyze 성격)계획 취소PRD 원안은 신규 엔드포인트였지만, ADR-003에서 기존 4개 API 오케스트레이션 유지로 확정 — 이 엔드포인트는 만들지 않음
결과 리포트 UI (배지/탭/카드)UI만 완성데이터는 전부 Math.random() 목업 (app/[lang]/scan/page.tsx)
다국어 카피(한/영)이미 존재dictionaries/{ko,en}.json의 scan.* 키
분석 진행 화면UI만 구현API 응답을 저장하지 않고 버림 (ProcessScreen.tsx)

2.2 목표

  • 기존 Lighthouse 결과 + AI 친화도(AEO 준비도) 0–100 점수 제공
  • 구조화 데이터 · 프롬프트 신호 · 인용 친화성 등 Lighthouse가 다루지 않는 영역을 룰 기반으로 보강
  • 이미 만들어진 /scan 리포트 화면에 실제 분석 결과 연결
  • 외부 ML/유료 API 없이 기존 Puppeteer + 자체 파싱만으로 구현 (신규 라이브러리 추가 없음)

2.3 스코어링 규칙 (100점 배분)

pie showData
  title AI Preparedness 점수 배분 (100점 만점)
  "구조화 데이터 (최대 35)" : 35
  "AI 신호 (최대 25)" : 25
  "인용 친화성 (최대 20)" : 20
  "색인/미리보기/기타 (최대 20)" : 20

가점 규칙

  • 구조화 데이터: WebPage/Article/FAQPage/LocalBusiness 각 6점(최대 24) + JSON-LD 파싱 성공 6 + FAQPage 포함 +5
  • AI 신호: prompts.txt 10(존재) + 3(100–5,000자) + PromptObject 8 + FAQ 섹션 감지 +4
  • 인용 친화성: 본문 600–2,000단어 +8, 문장 중위 길이 8–24 +4, 헤딩 계층 적정 +4, TL;DR 감지 +4
  • 색인/기타: robots 허용 +5, canonical 적정 +5, og/twitter 충돌 無 +5, hreflang/viewport +5

벌점 규칙

  • noindex −10
  • canonical 다중/순환 −8
  • og:image width/height 미기재 또는 600px 미만 −4
  • JSON-LD 파싱 에러 −6

2.4 이번 스코프에서 의도적으로 뺀 것 (v0.2 후보)

  • og:image 실제 픽셀 크기 측정(이미지 다운로드/디코딩)
  • sitemap.xml 내 URL 개수 카운트(GET + XML 파싱)
  • 결과 캐시의 영속화(현재 무상태 API라 재시작 시 캐시 소실 — DB 도입 시점에 재검토)
  • PDF 리포트, 경쟁 URL 비교(최대 3개)

3. 유저 플로우 FLOW

원래는 AS-IS(현재 코드)와 TO-BE(PRD 원안)를 별도 다이어그램 두 개로 그렸으나, 기획 인터뷰를 거쳐 단일 목표 플로우로 통합했습니다. 결정 배경과 검토한 대안은 ADR-003에 있습니다.

백엔드 변경 필요 지점 — crawling API 응답 확장(구조화 데이터, prompts.txt, FAQ 섹션, hreflang, viewport, noindex, 본문 단어수/h2·h3, TL;DR 후보 등 AI 신호 원본 필드, PRD 3장 그대로)이 선행돼야 프론트 스코어링이 의미가 있습니다. "프론트에서 점수를 계산한다"는 결정이 "백엔드 작업이 없다"는 뜻은 아닙니다 — 원본 신호 추출은 여전히 백엔드(Puppeteer DOM 접근) 몫입니다.

3.2 이번엔 결정하지 않은 세부사항

  • prompts.txt 체크를 crawling 응답에 얹을지, robotsTxt 처럼 별도 경량 API(promptsTxt)로 뺄지
  • 동일 URL 1시간 캐시 도입 여부(PRD Day2 체크리스트의 선택 항목)

3.1은 2026-08-13 기획 인터뷰로 확정된 목표 상태이며, 아직 코드에는 반영되지 않았습니다.
