# Git 브랜치 전략 — Git Flow (Full)

## 배경

기존에는 `main` – `dev` – `feat/*` 3단 구조(release/hotfix가 빠진 축소판 Git Flow)로
운영했다. `meta-scan-api`의 `FRONT_URL`/`FRONT_TEST_URL`/`PUBLIC_URL` 환경변수 분리가
보여주듯 `dev`(스테이징)와 `main`(프로덕션)이 이미 서로 다른 배포 대상에 대응하고 있어,
이 구분을 유지하면서 배포 시점의 코드 동결(QA)과 프로덕션 긴급 패치 경로를 명확히 분리하기
위해 원조 Git Flow(Vincent Driessen, 2010)의 나머지 두 브랜치 타입(`release/*`, `hotfix/*`)을
마저 도입하기로 했다.

## 브랜치 구조

| 브랜치 | 수명 | 분기 출발점 | 역할 |
|---|---|---|---|
| `main` | 영구 | — | 항상 배포된(프로덕션) 상태만 담음. 커밋마다 버전 태그(예: `v1.2.0`)를 남기는 게 관례. |
| `dev` | 영구 | `main` | 다음 릴리즈를 위해 완료된 feature들이 모이는 통합 브랜치. 스테이징 환경(`FRONT_TEST_URL`)에 대응. |
| `feat/*` | 임시 | `dev` | 개별 기능/작업 브랜치. 완료되면 `dev`로 병합. |
| `release/*` | 임시 | `dev` | 배포 직전 동결 브랜치. 버전 번호 확정, 문서/버전 bump, 막판 버그픽스만 허용(신규 기능 금지). 완료되면 `main` + `dev` 양쪽에 병합하고 `main`에 태그. |
| `hotfix/*` | 임시 | `main` | 프로덕션 긴급 패치. `dev`를 거치지 않고 `main`에서 직접 분기. 완료되면 `main`(+ 태그) + `dev` 양쪽에 병합. |

## 워크플로우

```
feat/foo ──┐
feat/bar ──┼──► dev ──► release/1.2.0 ──► main (tag v1.2.0)
            │              │                  │
            └──────────────┴──── 백머지 ───────┘
                                              │
                                main ──► hotfix/1.2.1 ──► main (tag v1.2.1)
                                              └──────► dev (백머지)
```

**핵심 규칙**: `release/*`, `hotfix/*`에서 만든 수정은 반드시 `main`과 `dev` 양쪽에
백머지한다. 하나만 병합하면 다음 release 때 그 수정이 유실된다 — Git Flow에서 가장 흔한
실수 지점이다.

## 장단점

| | 내용 |
|---|---|
| 장점 | 배포 이력이 버전 태그로 명확히 남는다. 긴급 패치(`hotfix`)와 정기 개발(`feat`→`dev`) 경로가 분리되어 서로 섞이지 않는다. `release` 브랜치에서 코드 동결 기간을 두므로 배포 직전 QA 단계가 명시적으로 존재한다. |
| 단점 | 브랜치 5종 + 양방향 백머지 규칙을 매번 사람이 지켜야 한다 — CI 자동화 없이 수동으로 하면 실수(백머지 누락)로 이어지기 쉽다. 이 저장소엔 아직 GitHub Actions가 없어, 최소한 release 완료 시 main+dev 백머지 여부를 확인하는 체크리스트나 스크립트가 필요하다. |

## 이 저장소에 적용할 때 정할 것 (미해결)

- ~~**버전 스킴**~~ — 2026-09-03 결정: 첫 `release/*` 브랜치(`release/0.2.0`)에서 모노레포
  단일 버전(루트 + `meta-scan-api` + `meta-scan-front` 세 `package.json` 모두 동일 버전 번호)
  으로 정함 — 세 패키지가 이미 `0.1.0`으로 우연히 맞춰져 있던 상태를 그대로 공식 규칙화.
  패키지별 독립 버전(`api-v1.2.0` 등)은 채택하지 않음.
- **릴리즈 트리거**: `release/*`를 언제 딸지 — 정기 캐덴스(예: 주 1회)인지 기능 단위인지
  아직 결정하지 않았다.
- **hotfix 승인 기준**: `main`에서 바로 분기하는 예외 경로이므로 "언제 hotfix를 쓸지"(예:
  프로덕션 장애로 한정) 기준이 아직 없다.
- 커밋 컨벤션(`commitlint.config.mjs`, Conventional Commits)은 이 변경과 무관하게 그대로
  유지한다 — `release/*`에서는 보통 `chore(release): bump version to x.y.z` 커밋 하나만
  추가되는 정도.

위 항목이 정해지면 이 문서를 갱신하고, 정책으로 확정되면 `docs/adr/index.html`에 ADR로도
등록한다(레포 컨벤션상 결정 기록은 ADR에 남기게 되어 있음).
