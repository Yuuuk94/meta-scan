# 블로그 포스트 스타일 계약 — case-study → blog

이 문서는 `docs/case-study/*.md` 하나를 블로그 포스트 하나로 옮길 때 지켜야 할 말투와 구조 규칙입니다.
`blog-writer` 에이전트는 매 포스트 작성 전에 이 문서를 읽고 따릅니다. `docs/design/design-system.md`가
`publish-front`/`qa-front-publish`에게 갖는 위치와 같습니다 — 규칙이 바뀌면 여기만 고치면 됩니다.

## 말투

- **합쇼체(-습니다/-합니다)**. 반말체나 "-이다/-한다"체는 쓰지 않습니다.
- **단조롭게**. 감탄사, 느낌표, 수사의문문 남발, "혁신적", "게임체인저", "압도적" 같은 과장된 수식어를
  쓰지 않습니다. 사실과 근거를 순서대로 나열하는 어조를 유지합니다.
- 이모지·아이콘을 본문에 쓰지 않습니다.
- 문장은 짧게 끊습니다. 한 문장에 두 개 이상의 절을 욕심내지 않습니다.

**나쁜 예**: "이 결정 하나로 개발 속도가 완전히 달라졌습니다! 정말 놀라운 변화였는데요..."
**좋은 예**: "이 결정 이후 빌드 시간이 줄었습니다. 원인은 아래에서 다룹니다."

## 구조 — 기승전결 4단

포스트는 반드시 아래 4단을 순서대로 갖춥니다. 소제목은 그대로 쓰지 않아도 되지만(자연스러운
제목으로 바꿔도 됨), 각 단계가 하는 역할은 지킵니다.

1. **기 — 도입**: 이 case-study가 다루는 문제를 범용적으로 제시합니다. "왜 이런 고민이 생기는가"를
   meta-scan 얘기를 꺼내기 전에 먼저 설명합니다. 이 프로젝트를 몰라도 읽히는 문단이어야 합니다.
2. **승 — 전개**: 이 문제에 흔히 쓰이는 접근법/선택지를 비교합니다. `docs/case-study/` 원문의 "대안
   비교" 내용을 일반화해서 풀어씁니다. 여전히 범용적인 톤을 유지합니다(프로젝트 이름 최소화).
3. **전 — 전환/적용**: 여기서부터 meta-scan 얘기로 넘어갑니다. "우리는 왜, 무엇을 골랐는가"를
   구체적으로 씁니다 — 실제로 어떤 상황이었고(제약, 팀 상황, 이미 있던 코드), 어떤 대안을 왜
   제외했는지. 이 절이 이 포스트에서 가장 구체적인 부분입니다.
4. **결 — 결론**: 적용 결과(아직 구현 전이면 "아직 구현 전"이라고 명시)와, 다른 상황에도 옮길 수
   있는 일반화된 교훈을 짧게 정리합니다. meta-scan만의 이야기로 끝내지 않고 독자가 자기 프로젝트에
   대입할 수 있는 체크포인트로 마무리합니다.

## 범용성과 프로젝트 적용의 균형

- 기·승 단계에서는 "meta-scan"이라는 이름을 반복해서 꺼내지 않습니다. 일반 원칙으로 서술합니다.
- 전 단계에서만 프로젝트 이름과 구체적 세부사항(코드 경로, ADR 번호, 실제 트레이드오프)을 씁니다.
- 결 단계는 다시 범용 톤으로 돌아옵니다.

## 사실 검증

- 전 단계(프로젝트 적용부)의 모든 주장은 소스 `docs/case-study/<file>.md`에 실제로 쓰여 있는 내용만
  씁니다. 없는 내용을 있어 보이게 지어내지 않습니다.
- "구현 완료"와 "방향만 결정, 코드 미반영"을 구분해서 씁니다 — 소스 문서의 상태 표기를 그대로
  따릅니다(예: ADR 상태, "아직 구현 전" 문구).
- 기·승 단계의 일반론은 업계에서 널리 통용되는 수준의 설명만 씁니다. 근거 없는 통계나 출처를
  지어내지 않습니다.

## 포스트 형식

각 포스트는 `docs/blog/<slug>.md`로 저장하며 다음 프론트매터로 시작합니다:

```yaml
---
title: <포스트 제목>
source: docs/case-study/<원본파일>.md
date: <작성일, YYYY-MM-DD>
tags: [<주제 태그 1~3개>]
---
```

분량은 대략 800~1500단어(한글 기준) 사이를 기본으로 하되, 원본 문서가 다루는 대안 수/복잡도에 따라
조정합니다.

## 체크리스트 (작성 후 자가 점검)

- [ ] 기·승만 읽었을 때 meta-scan을 몰라도 이해되는가
- [ ] 전 단계의 모든 구체적 사실이 원본 case-study 문서에서 확인되는가
- [ ] 결 단계가 프로젝트 밖에서도 쓸 수 있는 교훈으로 끝나는가
- [ ] 과장된 수식어·느낌표·이모지가 없는가
- [ ] 합쇼체가 처음부터 끝까지 일관되는가
